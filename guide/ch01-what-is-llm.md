## 1.1 LLM 怎样处理和生成文本

### AI、机器学习、NLP 与 LLM 是什么关系

这几个词经常被混着用,但关系并不复杂:AI、机器学习和深度学习是一层层包含的,而 NLP 是应用领域。

- **AI(人工智能)**:最大的圈子,泛指"让机器做看起来需要智能的事"。它**不等于**机器学习——上世纪的国际象棋程序、专家系统,靠人写死的规则运行,也算 AI。
- **机器学习(ML)**:实现 AI 的一种方法:**不手写全部规则,而是给算法大量样例,让它从数据中归纳规律**。垃圾邮件过滤是典型:没人写得全"垃圾邮件判断规则",但可以用几万封标注过的邮件训练分类模型。
- **深度学习(DL)**:机器学习的分支,用多层神经网络从数据里学习表示。2012 年后,它与 GPU 等算力的发展共同推动了图像识别、语音识别等领域的许多进展。
- **NLP(自然语言处理)**:注意,它**不是一种方法,而是一个领域**——凡是"让机器处理人类语言"的任务(分词、翻译、摘要、情感分析……)都算 NLP。这个领域先后使用过手写规则、统计机器学习和深度学习;今天很多任务会使用 LLM,但传统方法仍在使用。
- **LLM(大语言模型)**:在大量数据上训练、能处理和生成语言的大型神经网络。当前多数常用 LLM 以 Transformer 为基础,但 LLM 并不等于 Transformer;也有把 Transformer 与其他结构混合的语言模型。

```text
这些方法的关系(层层嵌套):
AI 人工智能
 ├─ 规则式:人写规则(早期棋类程序、专家系统)
 └─ 机器学习 ML:从数据里学规律
     └─ 深度学习 DL:多层神经网络
         └─ 大型语言模型 LLM
             ├─ 常见:基于 Transformer
             └─ 也有其他结构或混合结构

NLP 是领域不是方法(让机器处理人类语言):
手写语法规则、统计机器学习、深度学习和 LLM 都可以参与
```

::: tip 一句话记忆
**包含关系:**AI ⊃ 机器学习 ⊃ 深度学习,LLM 属于深度学习;NLP 是"处理人类语言"的领域。

**前端类比:**"AI"不等于"LLM",正如"前端开发"不等于"React"。在常说的生成式 AI 中,LLM 主要生成和处理文本。
:::

### 语言模型到底在干什么:预测下一个 token

对本书关注的生成式 LLM,最常见的生成方式很直接:**给定已有文本,计算下一个 token 的概率分布**。token 是模型处理文本的基本单位,可能是一个字、一个词的一部分、标点或代码符号。部分模型训练时还会加入其他目标,但生成文本时通常仍按这个方式逐步产生 token。

比如你问 AI "中午吃什么?",模型会给可能接在后面的 token 分配不同概率,这些 token 最终可能组成"米饭"、"面条"或"饺子"等回答。生成程序可以总选概率最高的候选,也可以按概率抽样;模型 API 通常会提供相关参数,具体默认值因模型而异。


"预测下一个 token"听起来很简单,但模型在大量文本和代码上训练后,会表现出理解、推理和写代码等能力。在参数、数据质量和计算量合理搭配的条件下扩大训练,通常会改善总体表现,但我们仍无法只根据规模准确推断某项能力何时出现。1.3 会说明这对工程实现有什么影响。

::: info 一个直观的例子
给你 `"function add(a, b) { return a +"`,模型通常会给 ` b` 很高的概率,后面可能继续生成 `;` 或 ` }`。模型学到的不只是"代码长什么样",还包括经常一起出现的函数结构、类型和调用方式。
:::

代码并不是天然干净的数据:公开代码里也有 bug、缺少依赖、过时代码、生成文件和重复内容。它真正特殊的地方是**语法约束较强,而且许多结果可以由编译器、类型检查、lint 和测试自动验证**。因此 Code Agent 可以在生成后得到明确反馈并继续修改;这不等于模型单靠训练数据就能保证代码正确。


### Transformer 怎样用 attention 读取上下文

预测下一个 token 的前提,是利用前文信息。一个词的含义取决于上下文——"it" 指的是猫还是垫子,要看前文;同一个 "bank",在河岸和银行的语境里含义不同。

**Transformer 由 2017 年论文 *Attention Is All You Need* 提出,最初用于机器翻译。它把一排 token 加工成一排包含上下文信息的数值表示。**今天多数常用 LLM 以 Transformer 为基础,但也有语言模型把 Transformer 与其他序列处理结构混合使用。

它靠一个核心机制做到这一点:**自注意力(self-attention,下文简称 attention)**。

对本书关注的自回归生成模型,可以先粗略理解为:**每个 token 查看允许访问的位置,算出"我该多参考谁",再按权重汇总这些位置的信息**。生成侧通常只能查看当前位置及之前的 token;原始 Transformer 的编码器则可以查看整段输入。

![注意力权重示意:一个注意力头可能更关注 "cat",数字不是实测结果](/diagrams/ch01-attention.svg)

"加权汇总"可以粗略理解为:处理后,"it" 的内部表示会带上与 "cat" 相关的信息。它仍然只是一组数值,不能直接当成人类可读的"理解过程"。

再补两个配角(后面的章节会用到,这里混个脸熟即可):

- **前馈网络(FFN)**:attention 负责 token **之间**交换信息,FFN 负责分别处理每个位置刚汇总来的信息。一层的主要计算部分通常包含 attention 和 FFN,此外还有归一化、残差连接等操作。多层会重复更新这些表示(1.2 的 MoE 主要替换的就是 FFN)。
- **位置信息**:attention 计算本身不知道 token 的先后顺序,所以模型还要加入位置信息。具体做法有很多,例如绝对位置编码或旋转位置编码(RoPE),不能简单理解为只有一种固定写法。

对自回归生成使用的 decoder,还有一条重要规则——**因果掩码(causal mask):每个位置只能看当前位置和之前的 token,不能看后面的 token**。原始 Transformer 的 encoder 自注意力不使用这种因果限制。decoder 的掩码画成矩阵是一张下三角(`✓` 能看到,`✗` 被掩码遮住):

```text
       t1   t2   t3   t4
t1     ✓    ✗    ✗    ✗     ✓ = 能看到
t2     ✓    ✓    ✗    ✗     ✗ = 被掩码遮住
t3     ✓    ✓    ✓    ✗
t4     ✓    ✓    ✓    ✓
```

为什么必须遮?训练时会一次放入整段目标文本;如果不遮住后面的 token,模型就能直接看到答案。推理时后面的 token 本来也还不存在。

把主要步骤串起来,decoder-only Transformer 生成下一个 token 的简化过程是:

![decoder-only Transformer 生成下一个 token 的简化过程](/diagrams/ch01-pipeline.svg)

这套架构有一个重要的工程特点:**训练时可以并行计算同一段文本的多个位置;生成一条回答时,后一个 token 通常依赖前一个 token,所以仍有先后顺序。**服务端可以并行处理不同请求,也可以使用一次预测多个 token 等优化,但不能完全消除这条依赖。第 2 章介绍的 KV Cache 会减少生成每一步对前文的重复计算;没有它仍能生成,只是通常慢得多。

补一段历史:原始 Transformer 是为**翻译**设计的 encoder-decoder 结构——**encoder(编码器)**处理源语言,**decoder(解码器)**根据编码结果生成目标语言。GPT 采用只保留生成侧的 decoder-only 结构。今天很多文本生成模型沿用这条路线,但 encoder-only、encoder-decoder 和混合结构仍各有用途。

### GPT 路线组合了哪些做法

下面这些做法共同推动了 GPT 路线的发展,但要注意:**它们并不都是 GPT 首创,也不是一次完成的四项架构修改。**

**做法一:使用 decoder-only 结构。** GPT 用带因果掩码的 Transformer 处理已有 token 并预测后续 token。许多公开的文本生成模型沿用这种结构;未公开架构细节的模型不应凭产品行为推断。它也不是所有 LLM 的唯一结构。

**做法二:先在大量未逐条标注的文本上做生成式预训练。** 下一 token 来自原文本,不需要为每个样本人工填写答案,因此比完全依赖人工标注更容易扩大数据量。但训练数据仍受质量、版权、隐私、语言覆盖和算力限制,不能把"整个互联网"直接等同于可用训练集。

**做法三:利用 Transformer 的并行训练能力。** 训练时可以在一次前向计算中得到多个位置的预测结果。模型规模还依赖数据并行、模型切分、通信和数值精度等系统工程,不能只归因于因果掩码。

**后来得到的经验规律:Scaling Laws(规模定律)。** 2020 年的研究发现,在其测试范围内,训练损失会随参数量、数据量和计算量按较稳定的趋势下降;2022 年一项关于计算预算的研究又说明,参数和数据要合理搭配。它们能帮助估算训练投入,但不能保证某项具体能力在某个规模出现。GPT-3 论文展示了**少样本学习**:只在提示里给几个示例,模型无需更新参数也可能完成任务,但不同任务上的效果差异很大。

::: tip 一句话总结
Transformer 提供了适合并行训练的结构,GPT 路线把 decoder-only 与大规模生成式预训练结合起来。后续进步同时来自数据、模型结构、训练方法和推理系统,不是只靠扩大参数。
:::

### 模型为什么逐个 token 生成输出

模型生成回答时通常是**自回归(autoregressive)**的:产出一个 token,再根据已有 token 预测下一个,循环往复。

```text
输入: "解释一下闭包"
  → 产出 token A
  → 根据输入和 token A 产出 token B
  → 根据已有全部 token 继续生成 ...
```

工程上这意味着服务端可以边生成边返回。许多 API 使用 `stream: true` 返回一连串事件或文本片段,但**一个网络片段不保证正好对应一个 token,一个 token 也不等于一个字**。前端应按任意长度的片段追加和解析,不能依赖分片边界。

所以从工程上看,LLM API 可以作为流式接口消费——这直接引出 Agent 的一个执行时机设计点:工具参数什么时候才算完整、什么时候可以开始执行?第 4 章比较执行时机,第 19 章再讲前端怎样解析和显示流式事件。

### 对话模型可能经过哪些训练

下面是一条常见路线,不是所有模型都严格按这三个阶段、这个顺序训练。实际训练可能跳过某步、重复多轮,也可能使用其他方法。

```text
① 预训练 (Pretrain)
   数据: 大量经过筛选的网页、书籍、代码等
   任务: 常见目标是预测下一个 token,也可能加入其他训练目标
   产出: 基础模型;已有语言能力,但通常没有专门优化成对话助手

② 监督微调 (SFT, Supervised Fine-Tuning)
   数据: 指令与高质量回答示例,数量和来源因模型而异
   任务: 学习遵循指令;若示例包含工具调用,也可以学习调用格式
   产出: 更适合对话和按要求输出的模型

③ 根据偏好或可验证结果继续训练
   信号: 人类或 AI 的偏好比较、测试结果、数学答案等
   方法: 根据人类反馈做强化学习(RLHF)、根据 AI 反馈训练、直接用偏好样本调整模型、根据可验证结果做强化学习等
   产出: 更符合指定行为和任务目标的模型
```

::: tip 对照记忆
可以把这条常见路线类比为程序员的成长:① **预训练** = 阅读大量材料;② **SFT** = 根据高质量示例学习怎样按要求回答;③ **偏好或奖励训练** = 根据反馈调整行为。DeepSeek-R1-Zero 直接从基础模型做强化学习、没有先做 SFT,就是"顺序并不固定"的公开例子。
:::

**为什么它能写代码?** 预训练数据中的代码让模型学到语法和常见实现模式;指令训练和后续训练还可以进一步强化编程行为。代码的部分错误能由编译器、类型检查、lint 和测试发现,这让 Agent 有机会得到反馈并修改。但测试可能不完整,需求也可能含糊,因此"能验证一部分"不等于"能自动证明全部正确"。第 3 章会说明 Agent 怎样负责工具、校验和安全控制。

## 1.2 模型怎样提升容量和推理能力

1.1 末尾我们看到:decoder-only 是当前常见路线之一,但不是唯一路线。这一节看 MoE 和思考模型怎样改变推理成本与使用方式——这些变化会影响你选哪个模型、怎么设计 Agent。

### 扩大模型规模会遇到什么问题

增加参数、数据和训练计算量通常会提高总体能力,但成本也随之增加;支持更长上下文还会增加推理时的计算与内存压力。MoE 尝试让每个 token 只使用部分参数,思考模型则在需要时投入更多推理计算,它们解决的是不同问题。

### MoE 怎样减少每个 token 的计算量

**Mixture of Experts(MoE,混合专家模型)** 是 DeepSeek-V3 及基于它训练的 DeepSeek-R1 所采用的重要技术。它要解决的问题是:怎样增加模型参数,又不让每个 token 都经过全部参数。

回到 1.1 的简化结构:Transformer 层的主要计算包括 attention 和 FFN。MoE 改的通常是 FFN:

- **稠密模型(dense)**:每层只有一个 FFN,所有 token 都走它——参数越多,每个 token 算得越多;
- **MoE 模型**:在部分层放置多份独立的 FFN,每一份叫一个**"专家"**;再加一个**路由器**,给每个 token 打分,只选择其中几份参与计算,其余跳过。具体有多少层使用 MoE、每次选几份,取决于模型设计。

![稠密模型与 MoE:路由器从 256 份专家里为每个 token 挑 8 份](/diagrams/ch01-moe.svg)

(DeepSeek-V3 的每个 **MoE 层**有 1 份共享专家和 256 份可选择的专家;每个 token 会使用共享专家,并从后者中选择 8 份。它的前三层仍使用普通 FFN。)

先拆掉一个常见误解:**"专家"不是**"数学专家/代码专家"这种预先规定的人类式分工——它只是个名字,本质是一份按需启用的 FFN。训练后可能观察到某些使用偏好,但应用开发者不能假定第几个专家固定负责某类知识。

::: info 一个类比:固定团队 vs 多个科室
**稠密模型**像一个固定团队:每个请求都经过全组人员。
**MoE** 像一家有许多科室的医院:分诊台(路由器)只为每个病人安排少数科室。医院仍要保存并调度全部科室,所以内存、设备间通信和部署难度不会随"只选少数"一起消失。
:::

算一笔账(DeepSeek-V3):

```text
总参数 671B —— 部署时必须让这些权重可访问,通常分布在多块加速卡上
每 token 激活约 37B —— 不到总量的 6%,不是所有参数都参与该 token 的计算
```

所以 MoE 在一定程度上把**总参数量**和**每个 token 经过的参数量**分开了。但"激活 37B"不等于"计算量和 37B 稠密模型完全相同":参数统计口径、attention 结构、路由和设备间通信都会影响结果。由此得到选型的实用结论:**比较 MoE 模型时,总参数、激活参数、实际吞吐、延迟和所需硬件都要看**。

MoE 的意义是在不让每个 token 都经过全部参数的前提下增加模型参数。它能降低一部分计算成本,但最终 API 价格还取决于训练、硬件、服务系统和厂商定价,不能只用 MoE 解释。

### 思考模型何时值得使用

这是 2024 年以来模型使用方式的一次重要变化,代表作 OpenAI o1、DeepSeek-R1。

**核心思想:在给出最终答案前,允许模型使用更多推理步骤和计算量。**这些步骤常以额外 token 表示,但不一定原样展示给用户:OpenAI o1 隐藏原始推理过程,DeepSeek-R1 等模型则可以返回推理内容。

```text
普通请求:  [问题] → 较少推理计算 → 最终答案
思考请求:  [问题] → 更多推理计算 → 最终答案
                       ↑
             原始过程可能可见,也可能隐藏
```

可以借用"快答 / 慢想"帮助理解成本差异,但这只是类比,不代表模型真的具有心理学中的两套思维系统。

::: warning 思考模型的代价与收益(这是 Agent 开发者必须算的账)
**代价**:模型服务可能生成大量推理 token,通常增加延迟和费用;具体是否计费、怎样展示,以 API 文档为准。
**收益**:在部分数学、编程和多步推理评估中,增加推理计算可以提高正确率,但不是任务越简单或推理越长就一定越好。

**结论:不要给所有任务都使用思考模型。** 简单的格式转换、CRUD 和文件摘要可以使用更快、更便宜的模型;复杂的 bug 定位和方案设计,才可能值得增加思考时间和成本。第 18 章 18.6 会讨论怎样按任务选择模型。
:::

::: tip 对 Code Agent 的三个现实影响
1. **成本结构取决于模型服务**:新一轮仍会产生新的推理计算;历史推理内容能否回传、是否进入上下文、能否命中缓存以及怎样计费,各家协议不同。接入时要读取所用 API 的当前文档,不能只按普通文本 token 推断。
2. **工具调用时机取决于协议**:有的模型先完成一段推理再请求工具,有的允许推理和工具调用交替出现。Agent 应按事件类型处理,并等待工具参数完整,不要假定固定顺序。
3. **外部检查不能减少**:推理能力提高不代表结果已被证明正确。测试、权限控制和副作用确认仍应由 Agent 执行。第 13、18 章会展开。
:::

## 1.3 为什么不能完全信任 LLM 的输出

前面两节讲了 LLM 是什么、怎样提升容量和推理能力,第 2 章说明了上下文为什么会增加延迟和成本。在进入 Agent 架构之前,还要理解当前模型的两个工程限制。研究会继续改善它们,但应用不能假定下一版模型就会让这些问题消失;后续 Agent 实现都要处理它们。

### 为什么模型的判断过程难以审计

传统程序把规则写在代码里,出错时可以定位到分支或变量。LLM 学到的行为则分散在大量权重和运行时的内部表示中,常见预训练目标是预测下一个 token,没有一份可以逐条查看的规则清单。研究者可以分析部分内部表示,但目前仍无法为每次回答还原一条可靠、完整的内部判断记录。

这给工程实现带来三个限制:

- **不能从回答中直接查出模型为何认定它正确。** 最终文本只能说明模型生成了什么,不能证明内容符合事实。
- **模型输出的“思考过程”仍然是生成文本。** 它可以帮助解题和检查,但不一定忠实记录内部计算,因此不能单独作为审计证据。
- **不能像修改普通代码那样修正某一条内部规则。** 应用开发者通常只能调整输入、模型和外围程序,再通过校验与评估确认效果。

### 为什么相同输入也可能得到不同结果

即使输入相同,LLM 的输出也不一定完全相同:

- **同一输入,输出可能不同。** 使用采样时,`temperature` 等参数会改变候选 token 的概率分布;即使使用低温度或服务端提供的固定 seed,很多 API 也只承诺"尽量复现",模型版本和后端计算变化仍可能改变结果。若采用本地固定模型、固定运行环境和确定性解码,则可以得到更强的可重复性。
- **小改动可能带来较大差异。** 提示词改一个词、消息顺序变化或工具定义变化,都可能影响结果。不能假定输入只改一点,输出质量也只改一点。
- **改进幅度要靠评估确认。** 改提示词、给例子、调采样参数或换模型都可能有效,也可能只对部分任务有效。不能仅凭原理得出"成功率会从 70% 提到 85%",但可以用固定测试集和多次运行估计变化。

### 这些限制怎样影响 Agent 的实现

由于不能直接修改模型内部的判断规则,也不能只凭直觉预测改动收益,实现 Agent 时要坚持两件事:

1. **不要把模型输出当成已验证的业务规则**:关键输出要校验(第 4 章);失败后先分类,只有操作可安全重复或状态已经确认时,才自动重试超时、限流等暂时性错误,参数错误和权限拒绝应直接修正或停止(第 18 章);危险操作还要限制权限并支持恢复(第 13 章);
2. **用评估确认改动**:原理和经验可以帮助提出改进方案,实际收益仍要用固定测试任务和多次运行确认(第 18、22 章)。

::: tip 为什么不干脆等模型变强?
模型能力会持续提高,但输出仍需要验证。Agent 执行时间越长、权限越大、操作越难撤销,错误的代价就越高。因此即使换用更强模型,Agent 仍然要处理权限、校验、记录和恢复。
:::

## 本章小结

| 主题 | 一句话 | 对 Agent 开发的意义 |
|------|--------|-------------------|
| 自回归 LLM | 根据已有 token 计算下一个 token 的概率分布 | 生成结果不能直接当作正确事实,要由 Agent 检查 |
| Transformer 与 GPT 路线 | decoder-only、大规模生成式预训练和并行训练共同推动了发展;规模定律是后来的经验研究 | 单条回答仍按先后顺序生成,但训练和请求之间可以并行 |
| MoE | 在部分层设置多份专家,每个 token 只使用其中几份 | 总参数和激活参数都不等于实际速度,还要测吞吐、延迟和硬件需求 |
| 思考模型 | 最终回答前使用更多推理计算,原始过程不一定可见 | 可能提高复杂任务正确率,也会增加成本;外部验证仍不能省 |
| 判断过程难以审计,输出可能变化 | 生成的解释不等于完整内部记录;API 也未必保证完全复现 | 用外部证据、校验和多次评估确认效果 |
