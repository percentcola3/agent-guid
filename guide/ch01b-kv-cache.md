# 第 2 章 KV Cache 与前缀缓存

::: info 本章要解决的问题
KV Cache 是贯穿全书实现的底层原理,后续第 3、5、9、11、18 章都会反复用到:

- 单次生成怎样避免对前文的重复计算;
- 模型服务怎样跨请求复用相同前缀;
- 为什么上下文越长越贵越慢,Agent 要怎样组织上下文。

本章不使用数学公式，也没有代码。
:::

## 2.1 单次请求内怎样缓存 K 和 V

回到第 1 章 1.1 的 self-attention:在使用标准完整因果 attention 时,每个 token 要和**所有之前的 token**算相关性,而计算相关性需要每个 token 的两个向量:**K(Key,键)** 和 **V(Value,值)**。使用滑动窗口等做法的模型可能只查看部分历史。

关键洞察:**已生成部分的 K 和 V,在生成后续 token 时一成不变——存起来复用,不必每轮重算**。这个存起来的东西,就叫 **KV Cache**。

```text
生成第 N 个 token 时:
  需要第 1~N-1 个 token 的 K、V
  → 存着(KV Cache):直接拿来用 ✅
  → 没存:每生成一个 token 都重算全部历史 ❌(上下文越长,浪费越明显)
```

KV Cache 有三个后文会用到的属性:

1. **由推理引擎管理**——为了速度通常放在 GPU/TPU 的高速内存中,但也可以分布到多块设备,或临时移到 CPU 内存;不能一概说它只存在单块显卡里;
2. **体积随缓存的 token 数量线性增长**——它常是长上下文和高并发服务的重要内存开销;
3. **至少在当前生成过程中复用**——请求结束后是否立即释放、保留供相同前缀复用,取决于推理引擎和模型服务的策略。

## 2.2 模型服务怎样跨请求复用相同前缀

如果两次请求使用相同模型和相关配置,并具有相同的 token 前缀,对应的前缀计算就有机会跨请求复用。vLLM 等引擎公开实现了这种做法;一些模型 API 则把类似能力作为 **prompt caching(提示词缓存)** 提供。模型厂商通常不会公开全部底层调度细节,所以不要假定它一定靠"路由到同一台机器"实现。

![提示词缓存:相同前缀有机会复用已有计算](/diagrams/ch01-prefix-cache.svg)

不同 API 的使用方式并不相同:

- **服务端自动匹配**:服务端自动寻找相同前缀,通常不承诺每次命中。OpenAI API 和 Gemini 的隐式缓存使用这种方式。
- **客户端指定缓存内容**:不同服务的接口也不一样。Claude API 可以用 `cache_control` 自动选择或明确标记缓存结束位置;Gemini 的部分 API 可以创建并引用缓存对象。不能把两种接口写成同一个实现。
- **门槛、有效期和价格都不同**:有的按缓存读取打折,有的还收缓存写入或保存费用;最短 token 数和有效期也会随模型及服务更新。实现时应读取当前官方文档;若响应提供缓存 token 字段就直接监控,否则用相同请求的延迟和费用对照来验证。

对按前缀匹配的缓存,系统提示词、项目指令(AGENTS.md)、工具定义等稳定内容应尽量放在前面,动态内容放后面。如果中间某处发生变化,**变化之前的相同前缀仍可能复用,变化位置及后面的部分需要重新计算**;不是改一个字符就必然让此前全部缓存失效。工具定义的顺序和序列化结果也要稳定。

## 2.3 为什么上下文越长越贵越慢

KV Cache 不是免费的。以常见的多头或分组查询 attention 为例,单条序列的体积可以粗略估算为:

```text
KV Cache 体积
≈ 2(K 和 V)
 × 层数
 × KV head 数
 × 每个 head 的维度
 × 缓存 token 数
 × 每个数值的字节数
```

标准多头 attention 通常为每个查询头分别保存 K/V;分组查询或多查询 attention(GQA/MQA)会让多个查询头共用较少的 K/V,从而明显缩小缓存。DeepSeek-V3 使用的多头潜在 attention(MLA)还会先压缩相关表示,也不能直接套用"隐藏维度"计算。长上下文的缓存可能从数 GB 增长到数十 GB,具体取决于模型结构、数值精度和批量大小。

这就是为什么:

1. **长上下文通常更贵**:API 通常按输入 token 计费;对标准的完整 attention,处理新输入的计算量增长得更快。前缀缓存、滑动窗口 attention 和其他结构会改变实际成本,不能只用一个公式概括所有模型。
2. **上下文不是越多越好**:无关内容会占 token、增加内存和延迟,还可能降低模型找到关键信息的能力。这就是为什么 Agent 需要做**检索、压缩、精简**(第 9~11 章),而不是默认把整个代码库塞进去。
3. **长会话常会变慢**:对使用标准 attention 的生成模型,每个新 token 要读取更长的 K/V;更长的新输入也会增加首个输出出现前的处理时间。缓存命中和具体模型结构会影响实际幅度。

## 2.4 这对 Agent 实现意味着什么

记住这三条,你就明白了为什么需要仔细组织发给模型的上下文:

先给上下文做一份预算,不要把模型窗口全部当成可用的历史空间:

```text
可用于历史和检索内容的空间
= 模型上下文上限
- 稳定的系统提示、项目指令和工具定义
- 为本轮输出预留的空间
- 为工具结果、参数修复和失败重试预留的空间
```

这里每一项都应使用所选模型的 tokenizer 或 API 返回值实测。不同 provider 对输入、缓存读取、推理和输出的统计口径可能不同;最终计费和是否命中缓存,以服务端返回的 usage 与账单为准。

::: tip 结论 1:稳定的内容放最前面
系统提示词、AGENTS.md、工具定义等**不变的内容放上下文最前**,构成可缓存前缀;每轮都变的内容(用户消息、工具返回结果)放后面。
→ 详见第 3 章(架构)、第 9~11 章(上下文与检索)
:::

::: tip 结论 2:别频繁改系统提示词
改动越靠前,需要重新计算的后续内容通常越多。所以**动态信息(当前目录、git 状态、时间)应放在稳定内容之后,不要每轮改写最前面的固定指令**。
→ 详见第 9 章(环境信息与上下文组装)
:::

::: tip 结论 3:上下文是稀缺资源
模型的上下文长度限制、内存和成本决定了输入不能无限增加。Agent 必须能**检索相关内容、删除可重新获取的内容,并在必要时压缩历史**。
→ 详见第 10~11 章(检索与压缩)、第 15 章(跨会话记忆)
:::

## 本章小结

| 主题 | 一句话 | 对 Agent 开发的意义 |
|------|--------|-------------------|
| KV Cache | 生成时缓存已计算过的 K 和 V,避免每轮重算前文 | “稳定内容放前面、动态内容放后面”的物理基础 |
| 跨请求前缀缓存 | 模型服务在多次请求之间复用相同前缀的计算 | 自动匹配、标记缓存位置和缓存对象的接口不同;监控实际命中,不要假定一定命中 |
| 上下文成本 | KV Cache 体积随缓存的 token 数线性增长,长上下文更贵更慢 | 上下文是稀缺资源,Agent 要做检索、压缩和精简 |
