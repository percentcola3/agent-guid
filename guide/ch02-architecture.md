# 第 3 章 Code Agent 除了 LLM 还需要什么

::: info 本章要解决的问题
第 1 章得到两个工程结论：模型只能根据当前上下文决定下一步，而且输出仍需外部检查。

要让模型真正完成代码任务，程序还必须负责准备信息、执行动作、控制风险和保存状态。本章先给出 Code Agent 的完整结构，后续章节再逐项实现。
:::

## 3.1 Agent 是完整系统，不只是模型

一个诱人的想法是:**只要模型够强,它自己就能当 Agent**。这话只对了一半。

来看一个真实场景:你让模型"把这个项目里所有 `console.log` 换成封装好的 `logger`"。一个**裸 LLM**(没有任何工具)能做什么?它只能"说"——告诉你应该怎么改,但它**改不了文件、跑不了测试、看不到改完的结果**。它甚至不知道项目里有哪些文件。

```text
裸 LLM:  "你应该先找到所有 console.log,然后逐个替换……"(然后呢?没有然后)
Agent:   grep "console.log" → 读到 23 处 → 逐个 edit → 跑测试 → 全绿 → 汇报
                                ↑ 这些"动作"靠的不是模型,是工具
```

本书所说的 **Agent**,始终指能够接收任务、调用模型、使用工具并管理整个执行过程的完整系统。LLM 只是其中负责**理解和决策**的部分;读取文件、执行命令和保存会话,由 Agent 内部位于模型之外的程序完成。

这部分程序有时被称为 **Harness**。它不是与 Agent 并列的另一个主体,而是 Agent 的内部实现。本章只用这个名称说明组成关系;后续章节默认直接说 Agent 或 Agent 的运行程序。

::: tip 一个判断标准
判断一个能力由模型还是 Agent 的运行程序提供,可以问一句:**换个更强的模型,这个能力会自动具备吗?** 会→主要是模型能力;不会→需要 Agent 的运行程序实现。"改文件""跑命令""回滚"显然是后者。
:::

不同 Code Agent 产品的主要差别,往往就在模型之外的程序怎样实现工具、权限、校验和恢复。只要 Agent 要处理执行时间长、风险高的真实业务,这些程序就不能省。

::: info 模型越强,为什么 Agent 的运行程序仍不能省
模型变强可能减少部分提示和纠错代码,但两类工作仍不能省:

- **限制模型错误的影响:**第 1 章讲过,模型输出可能变化,判断过程也难以完整审计;不可逆操作必须由程序保护。
- **处理运行时故障:**网络会断、进程会挂、用户会中断任务。这些问题需要第 14 章的会话记录、第 18 章的失败处理和第 19 章的恢复机制。
:::

## 3.2 Agent 的完整结构

把上一节的关系画出来:

![Agent 是完整运行系统,内部包含 LLM 和位于模型之外的运行程序](/diagrams/ch02-formula.svg)

其中各部分的职责是:

| Agent 内部的部分 | 它负责什么 |
|------|-----------|
| **LLM** | 理解输入、推理并决定下一步 |
| **Agent 运行程序（Harness）** | 调用模型、准备上下文、执行工具、控制风险并保存状态 |
| ↳ **上下文** | 向模型提供系统要求、对话历史、工具结果和检索到的代码 |
| ↳ **工具** | 真正读取文件、修改代码和执行命令 |

上下文和工具不是 Agent 之外的其他系统。它们都由 Agent 的运行程序管理:程序为每次模型请求准备上下文,并在模型要求调用工具时执行具体操作。

工具定义本身也是上下文的一部分。每次请求都要告诉模型有哪些工具、每个工具做什么以及需要哪些参数。

## 3.3 Agent 的运行程序需要负责什么

模型之外的程序主要负责下面四类工作。它们既是 Agent 的组成部分,也对应本书第二部分各篇的主要内容:

![Agent 运行程序负责上下文、工具、沙箱和权限,并限制错误、验证结果和支持恢复](/diagrams/ch02-pillars.svg)

### ① 上下文(Context):决定模型能看到什么

第 1 章讲过:LLM 是"看着上下文预测下一个 token"。**它看不到的东西,等于不存在**。所以上下文管理(给模型看什么、按什么顺序看、怎么压缩)直接决定了 Agent 的能力上限。

因此第 9~11 章会重点比较系统提示词、项目指令(AGENTS.md)、对话历史、工具结果、代码检索和上下文压缩。

::: tip 与第 1 章的联系
还记得 KV Cache 的三条结论吗?"稳定内容放前面""别改系统提示词""上下文容量有限"。上下文管理需要在缓存命中和信息完整之间取舍。
:::

### ② 工具(Tools):决定 Agent 能执行什么

工具是 Agent 与外部环境交互的接口。第 4~8 章和第 17 章分别说明基础工具(读/写/编辑/grep/glob/shell/code interpreter)、工具怎样注册和执行,以及怎样通过 MCP、Skill 和插件增加功能。

一个反复出现的原则:**优先提供可复用的工具,不要为每个任务单独写一个工具**。一个"代码解释器"通常比"计算器+排序器+格式化器"更通用,因为模型可以用代码组合出新的处理能力(第 8 章有展开)。

### ③ 沙箱(Sandbox):隔离命令和文件操作

Agent 要跑代码、跑命令,就得有个**隔离的执行环境**,防止它误删你的文件、外泄你的数据、把机器跑挂。第 13 章讲:网络出口控制、文件系统隔离、资源限额、持久会话与隔离的调和。

### ④ 权限(Permission):决定哪些操作需要禁止或批准

Agent 能做什么、不能做什么,谁批准。第 13 章讲批准模式(approve-every / on-failure / never)、危险命令拦截,以及怎样在真正读写数据的位置强制权限。

## 3.4 怎样限制错误、验证结果并在失败后恢复

上面四个部分解决"Agent 怎样做事",生产实现还必须回答三个问题:**怎样限制错误、怎样验证结果、失败后怎样恢复**。

这不是第五个独立模块,而是要在上下文、工具、沙箱和权限中分别实现。例如沙箱与权限负责限制危险操作,测试和类型检查负责验证修改,快照和 Git 负责恢复。下表中的 schema 指用 JSON 描述允许字段、类型和必填项的规则。

| 环节 | 作用 | Coding Agent 中的实现 |
|------|------|---------------------------|
| **约束** | 用代码强制的规则:做,也得按规矩做 | 模块边界、依赖规则、schema 强制、权限控制(即④) |
| **验证** | 自动判断对错 | 测试套件、lint、类型检查 |
| **纠正** | 出错怎么恢复 | git 回滚、沙箱快照、多级错误重试(第 18 章) |

::: tip 权限与其他约束有什么区别?
**权限管"能不能做",其他约束管"执行时必须符合哪些规则"。** 权限用于阻止危险操作;lint/CI 强制的依赖规则、schema 强制的数据结构,以及"退款金额不能超过订单金额"这类业务规则,不需要用户审批,但也必须由程序检查。
:::

实现时遵循四条原则(第 13、18 章详述):

::: tip 四条实现原则
1. **约束优先于指导** —— 能写进 lint/CI 强制的规则,就别写在文档里"建议"。前者是"做不了",后者只是"建议别做"。
2. **尽量自动验证** —— 测试、lint、类型检查能稳定重复执行,通常比只靠人工发现问题更早;是否值得投入,仍取决于项目规模和规则质量。
3. **反馈越快越结构化越好** —— 错误信息越接近出错时刻、越详细,Agent 纠正越快。
4. **失败后要能恢复** —— git 分支、沙箱和修改前的文件副本,可以把错误操作撤销。
:::

::: tip 先判断是否真的需要 Agent 自主决定下一步
不是所有带 LLM 的功能都需要反复调用工具。先看任务的下一步能否由程序提前确定:

| 任务特征 | 更简单的实现 |
|---|---|
| 步骤和分支都已知 | 普通代码或状态机 |
| 流程固定,只有某一步需要理解自然语言 | 只在该步骤调用一次 LLM |
| 下一步必须根据工具结果、环境状态或新证据决定 | Agent 工具循环 |
| 涉及发布、付款、删除或外发数据 | 可以使用 Agent,但关键条件仍由代码检查,必要时让人批准 |

自主循环的价值是处理无法预先列完的路径,代价是运行结果更难预测,还要补停止条件、预算、记录和恢复。能用固定流程解决时,不要为了“更像 Agent”而增加循环。
:::

Coding Agent 的一个有利条件是:软件工程已有测试、lint、类型、git 和 CI,其中一部分结果可以自动检查和回滚。这不代表代码任务天然容易,也不只取决于模型能力;缺少测试、需求含糊或跨系统副作用多时,同样很难可靠验证。

到这里,组成部分已经说明完了。接下来看这些部分在一轮任务里怎样配合。

::: info 后续章节怎样展开
下面的章节按一次任务逐步展开:

1. 第 4~5 章先把模型与工具之间的循环跑通;
2. 第 6~8 章实现文件、Shell、检索和交互工具;
3. 工具定义、执行结果和对话历史都会进入模型输入,因此第 9~12 章继续处理上下文;
4. 第 13 章集中说明沙箱和权限;
5. 第 14~19 章再处理会话、记忆、协作、扩展、可靠运行和 UI。

这是为了便于理解而采用的**讲解顺序**,不是建议先实现危险工具、最后才加安全控制。生产实现应从一开始限制权限和执行范围。
:::

## 3.5 一轮任务怎样执行

现在看一个 Agent 在一次 turn 中怎样工作。turn 指从用户发出一次请求,到 Agent 完成本轮回复或被中断的过程。这张图是全书最重要的图,后续每一章都在解释其中一段:

![一轮任务的完整过程:准备上下文、调用模型、执行工具并返回结果](/diagrams/ch02-turn-lifecycle.svg)

中间的 **③→④→⑤→⑥** 是 agentic loop:模型提出工具调用,程序执行并返回结果,再决定是否继续。它可以采用 ReAct 的 Reason→Act→Observe 提示方式,但生产接口未必显式暴露 Reason 或 Observe 阶段。

```text
伪代码(全书最重要的一段伪代码,第 4 章 4.3 会带着它逐段拆解工程细节):
messages = [系统提示, 用户输入]
while True:
    回复 = 调LLM(messages, tools)
    messages.append(回复)
    if 回复里没有工具调用:
        break                      # 模型说完了,本轮结束
    for 每个工具调用:
        结果 = 执行工具(可能经沙箱/权限)
        messages.append(结果)      # 回填,下一轮模型能看到
```

::: warning 一个根本事实:模型不会自己保存上一轮状态
每次推理都需要一份能表达当前对话的输入。有的 API 要求客户端每轮传入完整 `messages`;有的 API 允许传会话 id 或上一次响应 id,由服务端找回历史。传输形式可以不同,但**模型不会凭空记得上一轮**:Agent 的运行程序或模型服务必须重建等价的对话上下文。这带来两个贯穿全书的推论:

1. **历史必须有人管理**:Agent 可以自己记录并组装,也可以把部分会话状态交给模型服务;若要支持跨 provider 恢复和审计,通常仍需保存自己的事件或快照。事件日志是第 14 章会介绍的一种做法。
2. **未处理的历史会持续膨胀**:循环每转一圈,新消息就增加一截,而窗口是有限的。长任务动辄几十上百轮,历史怎么压缩、留什么删什么,是第 11 章要回答的问题。

第 1 章说上下文容量有限,在循环中的具体结果就是:**每执行一轮,历史都会变长**。
:::

::: tip 第 4 章预告
上面这段不到十行的伪代码,抽象出了 codex、grok-build 和 dsh 都具备的工具循环。第 4 章会逐步说明工具怎么声明给模型、输出怎么校验、并行与中断怎么处理,让你看懂生产实现还要多处理哪些问题。
:::

这里先说明两个会在后文展开的细节:

- **生成与执行的时机**:流式输出下,"什么时候开始执行工具"是个真实的设计点——codex 在单个输出项完成时即可启动,dsh 则等整个流聚合成完整消息后再执行(第 4、5、19 章)。
- **一个调用失败时影响谁**:并行调用里一个工具失败,不应该中止其他独立调用,也不应让错误直接终止整个 turn(第 4、18 章)。

## 3.6 AGENTS.md 应该放什么

回到上一节图中的 ②:稳定前缀里除了系统提示词和工具定义,还有 `AGENTS.md`。后续章节会反复用到这个文件,这里先说明它为什么重要。

`CLAUDE.md`、`AGENTS.md`、`.cursorrules` 是几种常见的**项目指令文件约定**,但不是一个全行业共用的标准。各产品支持的文件名、目录层级和加载时机不同;只有被当前 Agent 支持且命中其作用域的文件,才会加入模型上下文。

它们的作用类似**项目级指令**,但仍然低于系统/开发者指令。和给人类看的 README 不同,这里写的是 Agent 需要遵守的行为约定:

```markdown
# AGENTS.md(示例)
- 测试用 `pnpm test`,不要用 `npm test`
- 禁用 `any` 类型
- 不要改动 `migrations/` 目录
- 提交前必须跑 `pnpm lint`
```

不要把所有东西都堆进这一个文件。不同信息分别放到合适的位置,提示词会更短也更可靠:

| 内容 | 应放在哪里 |
|---|---|
| 必须始终满足的安全与架构规则 | 沙箱、权限、schema、lint/CI 等代码约束 |
| 稳定但需要模型理解的项目流程 | AGENTS.md / Skill / SOP |
| 难用规则描述的输出风格 | 少量、代表性的 few-shot(少样本)示例 |
| cwd、分支、预算、后台任务、当前目标等动态状态 | 第 9 章由系统生成并标记来源的状态栏,不要改写稳定的系统提示词前缀 |

同一规则如果已经由代码强制,AGENTS.md 可以解释"为什么"和失败后的修复方式,但不能只写文档而不做代码检查。

::: tip 为什么它特别值钱(回到 KV Cache)
回到第 2 章:稳定的内容放前面,就有更大机会复用已有的前缀缓存。**AGENTS.md 是典型的"稳定前缀"**——它通常不随单次任务变化,因此对 KV Cache 友好;是否实际命中仍取决于 provider、模型、TTL 和缓存门槛。

这也是一条更广的原则:**让完成任务所需的知识能被 Agent 访问**。稳定的项目规则适合版本化到代码库;临时决定也可以来自 issue、PR、知识库或用户补充。只存在于口头沟通中的约定无法被自动读取,容易造成遗漏。对远程协作友好的文档习惯,通常也能帮助 AI Agent。
:::

本书就用 `AGENTS.md` 作为项目指令文件的统称。

## 3.7 三个参考项目怎样组织这些部分

本书从第 4 章起,会反复对照三个真实项目:

- **codex**(OpenAI,Rust,生产级)
- **grok-build**(SpaceXAI,Rust,生产级)
- **DeepSeek Harness**(DeepSeek 官方,TypeScript,下文简称 dsh)

dsh 功能较完整,但仓库仍标为 developer preview,不承诺兼容性。

这里先比较它们怎样组织代码和功能,后续每章再看具体实现。下面的模块路径均按本书核对时的代码快照记录。

::: tip 为什么 dsh 对本书特别重要
dsh 是三个参考项目中唯一的 **TypeScript** 实现——与本书读者的主要开发语言一致,核心循环也和第 4 章的最简循环结构相同。它与另外两家最大的区别是:大部分功能都注册为 Cordis 插件,连 agent loop 本身也可以替换;`dsh web` 根据一份 YAML 清单选择要加载的插件。
:::

### 按 Agent 的组成部分对照

| 比较项 | codex(OpenAI,Rust) | grok-build(SpaceXAI,Rust) | dsh(DeepSeek,TypeScript) |
|------|---------------------|---------------------------|---------------------------|
| **整体设计** | 一个主程序,内部按职责拆分 | 多个 Rust crate 按职责拆分,部分能力有多种实现 | 大部分功能由 Cordis 插件提供 |
| **主循环/调度** | `codex-core`(`codex_thread.rs`、`session/turn.rs`) | `xai-grok-shell`(leader/agent/session)+ `xai-grok-agent` | `packages/core/agent-loop/src/agent.ts` 的 `ReactLoopAgent` |
| **消息历史** | 内存消息 + rollout 记录 | chat-state 对象 | 只追加事件日志,需要时由 `deriveMessages()` 生成消息 |
| **工具注册** | `core/src/tools/`(router+registry)+ 顶层独立 `tools/` crate(定义/执行) | `xai-grok-tools`(implementations/registry) | `core/tools` 服务 + `defineTool()` 工厂 |
| **文件编辑** | `apply-patch` crate(freeform 语法) | **三方案并存**:原生 hashline + 移植 codex/opencode 编辑器 | **双方案并存**:`edit`(old/new+版本乐观锁)+ `str_replace_editor`(Anthropic 移植) |
| **Shell 执行** | `exec_command`/`write_stdin`(用 yield 统一处理前后台) | `bash`(前台和后台分别处理)+ task 工具族 | `tool-bash`(非会话化 + jobs 后台 + 输出超限后写入文件) |
| **沙箱** | `linux-sandbox`+`sandboxing`(seatbelt/bwrap/landlock)+`execpolicy` 等 | `xai-grok-sandbox` | `sandbox/` 组(bwrap/Landlock/Seatbelt/Win ACL)三档模式 |
| **上下文管理** | `context-fragments` crate(`ContextualUserFragment` trait + token 上限) | (分散在 agent/compaction + session-search) | `core/system-prompt`(section 注册表)+ `compaction`(阈值触发) |
| **代码检索** | **无专用检索工具**:模型用 shell 跑 `rg`/`find` | 专用 `grep`(ripgrep)+`read_file`+`list_dir`+可选 LSP(Language Server Protocol,语言服务器接口);`codebase-graph` 仅服务 Web 客户端导航 | `read`/`grep`/`glob`(ripgrep 驱动)+ `lsp` 工具 |
| **记忆/持久化** | `codex-memories-read`+`-write`+`ext/memories`+`rollout` | `xai-grok-memory`(sqlite-vec FTS5/向量)+`xai-sqlite-journal` | **JSONL(zstd)/SQLite 双后端**,事件溯源 |
| **多 Agent** | `multi_agents_v2/`+`agent-graph-store`(记录 spawn 父子关系;当前 V2 不按 max depth 拒绝) | `xai-grok-subagent-resolution`+`xai-grok-agent` | `subagent/` 组(spawn/fork,甚至能把 Codex/Claude Code 当子 agent 驱动) |
| **MCP(Model Context Protocol,统一连接外部工具的协议)** | `codex-mcp`+`mcp.rs` handler+`mcp-server`/`rmcp-client` | `xai-grok-mcp` | `mcp-client` 插件(`mcp__server__tool`) |
| **扩展机制** | `skills`+`plugin`+`connectors`+`core-plugins` | `xai-grok-plugin-marketplace` | **Cordis 插件**(npm 包 + YAML 组合) |
| **运行记录与监控** | `otel`+`rollout-trace`+`analytics` | `xai-grok-telemetry`+`xai-crash-handler`+`xai-mixpanel` | 会话事件全部写入磁盘 + telemetry 插件 |

### 为什么同一个 Agent 会保留多种编辑器

看“文件编辑”那一行，两个项目都保留了多种实现：

- grok-build 同时内置三种编辑器：原生 hashline、移植 codex 的 apply_patch、移植 opencode 的 edit；
- dsh 同时保留两种：自家的 `edit`，以及移植自 Anthropic 的 `str_replace_editor`。

不同模型、不同任务适合的编辑方式并不相同。与其押注一种实现，项目也可以保留多种方案并按需选择。这正是本书反复强调的原则：**同一个问题没有唯一答案，只有适合不同场景的取舍。** 第 6 章会把这些方案逐一比较。

::: tip 三种规模,三种学法
- **dsh**(TypeScript):适合本书的 TS 读者精读——`ReactLoopAgent` 与第 4 章的最简循环使用同一种语言,实现方式也接近,便于逐段对照。
- **codex**(Rust):功能完整,沙箱、权限以及日志/指标/追踪支持很全。
- **grok-build**(多 crate):按职责拆分较细,适合按 crate 阅读。行数和 crate 数会随版本快速变化,不作为长期结论。
:::
