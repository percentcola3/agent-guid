# 第 8 章 检索、计划、询问与多工具执行

::: info 本章要解决的问题
第 6、7 章实现了文件编辑和 Shell，但完整任务还会遇到三类需求：

- 动手前，用 glob 和 grep 找到相关代码；
- 任务较长时，记录计划，并在信息不足时询问用户；
- 同一轮出现多个调用时，决定提供哪些工具、哪些调用可以同时执行。

本章补齐这些工具层能力。
:::

## 8.1 检索工具:grep 与 glob

glob 按文件名查找,grep 按内容查找;工具本身并不复杂。三家都让模型使用 ripgrep 驱动的查找能力,codex 没有为它们提供专用工具,而是让模型通过 Shell 运行 `rg`。

这不是偷懒,而是一条值得先立下的原则:**尽可能实现通用的工具,而不是专有工具。** 一个 Shell 执行器能顶掉计算器、排序器、格式化器等一整排专有工具——模型可以用命令组合出这些能力;反过来,每个专有工具都要占用上下文(8.4)、单独维护和评测。codex 是这条原则最彻底的实践者:检索和读文件都交给 Shell(`rg`、`cat`),工具面因此最窄。

专有工具并非不该存在,它们换的是另一些东西:**结构化输出**(专用 grep 工具返回明确的匹配列表,不用解析命令输出)、**更细的权限边界**(专用读工具可以限制目录,Shell 很难)、以及**不依赖模型写对命令**。grok 和 dsh 保留专用检索工具,取的就是这几样。

更难的是**怎样用这些工具找到真正相关的代码**。多步检索和"要不要建索引"的取舍留到第 10 章讨论。

## 8.2 规划类工具:todo 与 plan

**长任务到底难在哪。** 先把问题摆出来。模型的"工作记忆"就是上下文,而上下文是被不断冲刷的:一个跨十几轮的任务,完整目标只出现在第一轮;之后检索结果、文件内容、命令输出源源涌入,目标的占比越来越小。典型事故有三类:

```text
① 遗漏:模型宣布"任务完成"——最初要求的三个改动只做了两个
② 打转:在一个子问题上越钻越深,反复读同一批文件,忘了这只是第一步
③ 偏航:用户中途补一句"顺便补下测试",做完测试就把主线丢了
```

这和一个只有聊天记录、没有任务清单的实习生一样:记录越长,开头那句叮嘱的分量越轻。

**方案:把目标从聊天记录里拿出来,放到一块外置任务板上。** 任务开工时列出步骤,每完成一步更新状态。对照三类事故:遗漏——板上有未勾选项,"提前宣布完成"会被一眼看穿;打转——当前步骤始终可见;偏航——主线在板上,插曲做完回得来。

三家的实现策略不同,核心差异是**每轮把多少计划内容放回上下文**:

- **codex `update_plan`**:计划写进会话事件流,主要给 UI 展示;回给模型的只有固定一句 "Plan updated"。最省 token,但模型仍要靠自己从历史里找回目标——适合有人在旁边盯进度的场景
- **grok `todo_write` + 提醒器**:每次更新把全量清单作为工具结果返回,任务板始终"新鲜"地留在上下文里;发现模型偏离 todo 时还会主动注入提醒(每个任务最多 2 次,防唠叨)。目标最难丢,代价是 token
- **dsh `todo_write`**:整表替换语义,每次写入记一条会话事件(重放时以最后一次为准);进上下文的只有一句"已更新,X 项待办"。居中,换来会话可重放

**Plan 模式是另一层保护:先规划、经批准、再动手。** 长任务最大的浪费不是某一步慢,而是一头扎进错误方向改了半小时——纠错发生得越早越便宜。Plan 模式让模型先只读规划、产出计划交用户批准,再进入执行;codex 在此模式下直接拒绝执行类调用。计划保存为**文件还是会话状态**也有讲究:grok 写进磁盘文件、退出时读回呈批(用户可以直接改文件);dsh 把模式开关本身记成会话事件(跨会话可查)。

::: tip 一句话
规划类工具的本质不是"记录",而是**对抗上下文冲刷**——让"现在该做什么"始终以完整、新鲜的形式出现在模型眼前。
:::

## 8.3 用户交互类工具:问用户

模型遇到会实质影响结果的不确定信息时,应把选择交还给用户。三家的提问工具都支持等待用户回答和展示带说明的选项;具体是否支持多选、推荐项和自由输入,由各自客户端决定。codex 的客户端还会自动追加 "Other" 让用户自由输入。

一个值得注意的共性是:**三家抽查到的提问路径都没有自行替用户选择答案**。等待期间可以由外层取消回合,并把本次提问记为已取消。

如果产品要为提问设置超时,超时后的默认行为必须保守,例如停止任务或继续等待,不能擅自批准高风险操作。

## 8.4 工具太多怎么办

每个直接提供给模型的工具 schema 都会占用上下文,工具越多、schema 越长,留给任务本身的空间就越小;而且候选一多,模型也更容易选错工具。常见对策有三种:

1. **少而通用**:保留基础工具,用 Skill 文档描述流程,避免每个任务都新增一个工具
2. **延迟加载**:codex 的 `tool_search`——完整 schema 不进上下文,模型先检索工具目录,匹配的工具下一轮才提供给它。Anthropic 公布的一组实验中,按需检索把工具使用准确率从 49% 提升到 74%;实际收益仍取决于工具集与任务
3. **动态装配**:dsh 按 preset 组装工具集,会话开始时决定有哪些工具

## 8.5 多个调用怎样执行

一条回复里模型可能一次发起多个工具调用。系统要回答三个问题:

**谁决定并行?** 模型只负责"发起":它把多个调用放进同一条消息,**并不声明它们互不依赖**。能不能并行的判定权在工具元数据——只有工具显式声明并发安全才进并行池,默认串行(第 4 章 4.5.1 的结论在这里落地)。

**什么时候开始执行?** codex 在**单个调用的参数一生成完**就启动执行,不等整条消息;dsh 等整条消息收集完再统一执行。前者可以降低等待时间,后者更容易在执行前看到完整调用列表。

**失败怎么处理?** 只有确认同批调用彼此独立时,一个调用失败才只产生它自己的错误结果;存在依赖时,后续调用应停止或标记为未执行(第 4 章 4.5.1)。

对于步骤固定、数据量较大的操作,还可以让模型一次生成一段脚本,把"读文件 → 解析 → 再读 → 汇总"放在代码里执行。中间变量留在执行环境,只有最终结果返回模型。

这种做法能显著省 token——中间数据留在执行环境里,不经过模型;实际幅度取决于中间数据量和任务结构。这也是 code interpreter 的价值之一:让代码组合现有能力,减少模型与工具之间的往返。

## 【对比小结】

| | codex | grok-build | dsh |
|---|-------|-----------|-----|
| 规划 | `update_plan` 只回 "Plan updated",列表给 UI | todo 摘要随结果返回 + 偏离提醒(≤2 次) | todo 整表替换,记会话事件 |
| Plan 模式 | 与 checklist 分离,规划期禁用执行工具 | 计划写磁盘文件,退出时读回呈批 | 模式开关是会话事件,计划经人工审批 |
| 问用户 | `request_user_input`,客户端自动加 "Other" | `ask_user_question`,取消不算错误 | `ask_user_question`,推荐项标注 |
| 工具过多 | `tool_search` 延迟加载 | 工具面最宽,按需配置 | preset 按会话装配 |
| 执行时机 | 参数一生成完即执行 | 单输出项完成即启动 | 整条消息聚合后执行 |

**核心取舍:**计划内容放回上下文多少、一次提供多少工具、工具调用多早开始执行。三家的选择不同,选型取决于上下文预算、延迟要求和调用之间是否存在依赖。

## 本章小结

- 工具选择优先通用:Shell 一类通用工具能组合出大量专有能力,codex 因此工具面最窄;专有工具换的是结构化输出、细权限和不依赖模型写对命令
- 检索工具本身简单,怎么用好是第 10 章的事
- 长任务的敌人是上下文冲刷(遗漏/打转/偏航);规划工具把目标放上外置任务板,三家差异在每轮放回多少——全量清单+偏离提醒 / 只回确认 / 一句统计
- 问用户时应等待用户回答;取消或超时由外层处理,默认行为不能擅自批准高风险操作
- 工具定义本身占上下文;具体开销取决于工具数量和 schema,对策是少而通用、延迟加载、按会话装配
- 多工具执行要明确谁可以并发、何时开始、失败后是否继续;只有彼此独立的调用才能隔离失败

到这里,工具层已经基本完整。与此同时,每个工具 schema、搜索结果、执行日志和计划都会进入模型输入;任务越长,问题就越快从"Agent 能不能执行"转为"模型应该看到什么、按什么顺序看到"。下一章从上下文的组成开始处理这个问题。
