# 第 13 章 跑得安全：沙箱与权限约束

::: info 本章要解决的问题
第 12 章把网页等外部内容接入了上下文。这些内容可能诱导模型读取私有文件、运行命令或向外发送数据；来源标记和提示只能降低误判概率，不能强制阻止操作。

本章回答四个问题：**攻击需要哪些条件、操作系统怎样限制命令、执行前怎样检查、用户怎样批准一次额外权限**。

沙箱负责限制当下的操作。审批结果、工具是否启动和副作用是否发生，还要能够在崩溃后确认；第 14 章会继续解决这个问题。
:::

## 13.1 哪三种能力同时出现时最危险?

检查 Agent 是否高危,可以直接看 Simon Willison 总结的三件事。三条同时具备,攻击就能完成:

```text
① 访问私有数据     —— Agent 能读你的文件、SSH key、环境变量
② 暴露于不可信内容 —— 它读的网页/issue/日志里可能藏着恶意指令(提示注入)
③ 具备外部通信能力 —— 它能发请求、执行命令,数据出得去

攻击路径:恶意指令藏在网页里 → 注入 Agent → 读取 ~/.ssh → curl 外传
```

::: warning 第四维:持久记忆是放大器
长期记忆还会扩大影响范围:恶意内容写入 MEMORY.md 后,可能在几天后的会话中再次进入模型输入。所以记忆写入需要与外部内容同等的信任审查(第 15 章详述)。
:::

需要在三个位置分别处理:读取内容时标明来源并分开指令与数据(第 9 章);执行操作时使用沙箱并请求审批(本章);启动进程时不要把不需要的凭证交给它。本章重点讨论第二项。

## 13.2 操作系统怎样限制文件、网络和系统调用?

三个项目组合使用下面几种操作系统能力和用户态工具:

| 机制 | 平台 | 限制什么 | 特点 |
|------|------|---------|------|
| **Seatbelt**(sandbox-exec) | macOS | 文件/进程/mach 服务的系统调用 | 声明式策略(SBPL),`(deny default)` 起步逐项放行 |
| **Landlock** | Linux | 文件路径的读写(内核自带,无需 root) | **不可逆**:进程对自己上了锁,后代全继承 |
| **seccomp** | Linux | 按系统调用及部分参数放行/拒绝 | 可阻止新建 socket 等调用;已有文件描述符和未覆盖调用仍要单独考虑 |
| **bwrap**(bubblewrap) | Linux 用户态工具 | 借助 mount/user/pid 等 namespace 组装文件系统与进程视图 | 可用 `--ro-bind / /` 把宿主根挂为只读,但 bwrap 本身不等于完整容器平台 |

### 为什么要先限制自己再 exec?

正确的上锁顺序是：**先给自己上锁，然后才启动你的命令**。限制规则会跨进程启动继承，所以目标进程及其所有后代从**第一个字节**起就被限制——不存在"先启动、再上锁"之间的空窗期。`sudo` 在 exec 前切换凭据、`sandbox-exec` 在启动目标前应用策略，遵循的都是这个顺序；把流程画成"目标先执行、之后才限制"就错了。

配套一条容易漏的工程细节：沙箱自身启动失败时，调用方必须能区分"沙箱没装上"和"命令自己失败了"——只看退出码不够（两者可能撞同一个码），要用专门的诊断标记判断；安装失败时绝不能继续运行目标。

## 13.3 用户需要看懂哪三档权限?

为了横向比较,本书把三家的配置近似映射成三类。它们不是行业统一标准,实际边界要看平台和后端:

```text
read-only           只读意图:除运行所需的特殊设备/临时位置外不允许文件写入
workspace-write     工作区写意图:允许指定工作区和后端定义的临时位置
danger-full-access  绕过这一层文件沙箱;不代表系统其他权限自动提升
```

三家的档位名称和粒度各不相同:有的在三档之外加了**网络开关**旋钮;有的档位更细、还允许继承内置档位做自定义。映射成三类只是为了横向讨论,两点必须记住:**档位词汇只描述文件效果**,网络与进程可见性不在其中;各家默认档位还可能被部署配置覆盖。

三类便于向读者解释"只许看 / 在项目里干活 / 绕过文件限制",但不能代替具体能力清单。Windows 后端目前只限制写入、不限制读取与网络,属于部分实现——所以界面必须展示**实际生效的后端和限制范围**,而不是一个档位名。

## 13.4 命令执行前由谁判断能不能跑?

命令执行前,三家采用不同检查方式,下图直接比较检查发生的位置:

![命令由执行前检查还是操作系统限制](/diagrams/ch07-security-boundary.svg)

### codex:执行前把命令拆开逐层判断

codex 在命令执行前让它**依次经过多层判断**:

```text
把命令拆成多段(管道/子 shell 拆开逐段看)
  → 规则引擎(声明式前缀规则:放行 / 需批 / 禁止)
  → 无规则命中 → 安全命令白名单 + 危险命令启发式
  → 结合审批档位,输出:放行 / 需人工批 / 禁止(附原因)
批准后还能把新前缀"学"回规则库
```

配套沙箱同样分层：先用系统调用过滤自限，再做文件系统隔离；macOS 上还**保护 `.git/hooks`**——防止 Agent 通过写 git 钩子实现提权持久化，这是一个容易被忽略的持久化通道。

### grok:启动时上锁,执行前做最多的静态检查

grok 在 Agent 进程启动阶段就应用沙箱（Landlock 或 Seatbelt，部分配置再叠加 bwrap），已施加的限制不可逆；网络限制则取决于启动路径，不能笼统写成"所有子进程都被断网"。之后在命令执行前做三家中最多的静态检查：用 AST 检查文件写入路径、环境变量泄露、exec 调用，以及内容无法提前知道的 shell（`bash -c "$X"`）。两条铁律：**解析失败就必须人工审批**，绝不自动放行；hooks 目录要真正只读，而不只是配置里写写。

失败处理也不是统一的"警告后继续"：基础档位不支持时可能记录未应用状态，带必需限制的配置则直接拒绝启动——实现时要区分"已应用 / 未应用 / 出错"三种结果。它还有一个 auto 档：先让 **LLM 分类器**预检，超时、不可用或连续拒绝时转人工。

### dsh:不分析命令,让操作系统拒绝越界

dsh 选择另一种做法:**不解析命令,也不使用黑名单**。每次工具调用时,按平台选择后端在执行边界限制文件访问(Linux 用 bwrap 或 Landlock,macOS 用 Seatbelt,Windows 用 ACL——注意 ACL 后端是**部分实现**:只限写入,不限读取、网络与进程可见性);启动前先实际检查所需后端能否使用,缺失就拒绝执行。是否允许写文件,最终由操作系统判断。

::: tip 三种做法分别得到什么、付出什么?
| | codex | grok | dsh |
|---|---|---|---|
| 分析时机 | 执行前(规则+AST) | 执行前(AST+环境/exec 检查) | 不分析命令文本 |
| 强制位置 | 命令分析 + OS 沙箱 | 命令分析 + 启动时 OS 限制 | 每次调用选择 bwrap/Landlock/Seatbelt/Windows ACL |
| 判断偏差 | 规则和 AST 可能误判;批准后可学回规则库 | 规则覆盖广,仍可能误判或转人工 | 不判断命令意图,但路径策略仍可能拒绝合法操作 |
| 提前告知用户 | 可根据分析结果说明 | 可根据分析结果说明 | 通常在执行被拒后说明 |
| 主要代价 | 维护规则、解析器和沙箱 | 维护更多命令规则与 profile | 维护多平台后端;Windows 目前只是部分限制 |

**dsh 不分析 Shell 命令含义,而是在执行边界选择平台后端限制文件访问。** 这样不需要维护命令分析引擎,但实现并不“零复杂度”,模型也通常要在执行被拒后才知道具体越界位置。codex/grok 在执行前分析命令,能提前向用户说明风险;代价是要持续覆盖 Shell 众多可组合的写法。
:::

## 13.5 命令被拒后怎样申请一次额外权限?

安全机制的另一半是**人机协议**:用户怎么批准?模型被拒后能做什么?

**grok 的 `description` 最终显示在哪里?** 第 7 章提到 grok bash 工具必须填写 `description`。它会成为审批弹窗的标题,让用户看到模型为什么要运行命令,例如 “Allow *run tests for the auth module*?”。因此这个字段既是工具参数,也是给用户看的说明。

**codex:独立的扩权工具。** `request_permissions` 让模型请求额外文件系统/网络权限。审批档位为 Never 或该功能未启用时,handler 返回**空的额外权限集合**,不是执行成功;可交互时用户能批准 turn 级或 session 级权限,批准结果再由后续调用使用。

**dsh:在原调用上申请一次更高权限。** 命令在沙箱内被拒时,返回体自动附加两个标记:**拒绝原因** + **申请提示**(教模型"同一命令带目标权限和理由重试一次")。重试要过三道校验:

```text
参数成对:目标权限档 + 申请理由,缺一不可
严格变宽:read-only → workspace-write → danger-full-access,只能单向升
结果两态:allowed-once → 仅本次调用生效(下次照旧受限)
          rejected     → 终局,禁止绕行
```

严格变宽保证权限只能**单向**升,单次生效保证不产生持久污染——一次审批恰好覆盖一次越界,粒度最干净。审批的一问一答全部落会话日志,可审计。

### 高风险操作为什么要先准备,批准后再提交?

如果审批弹窗只展示模型几轮前写下的参数,用户批准时真实状态可能已经变化。发布、删除、转账、修改云资源等操作可以拆成两个工具阶段:

```text
prepare  读取当前真实状态 → 规范化参数 → 生成预览
         → 返回 operationId + stateRevision + expiresAt
approve  用户批准这份确定的预览
commit   再读当前状态 → 核对 operationId、revision、有效期和权限 → 执行一次
```

`commit` 必须使用幂等键,重复请求只能得到同一个结果。若客户端在提交后超时,先用 `operationId` 查询状态,不要直接重试副作用。状态版本已经变化时应让旧批准失效并重新准备,不能把用户对旧预览的同意套到新内容上。

这套做法不是三个参考项目的统一接口,而是面向高风险业务工具的可选设计。普通只读查询不必都增加两阶段操作。

### 浏览器断线后,审批请求怎样恢复?

Web UI 里最容易漏掉的是:审批不是一条普通 toast,而是**服务端发给客户端、等待恰好一次回答的 request**。协议至少需要 `approvalId + sessionId + turnId + toolCallId + expiresAt`:

```text
requested → decided(allow-once/reject)   正常结束
          → resolved(被其他路径解决)     客户端关闭旧弹窗
          → expired/disconnected         拒绝执行,绝不默认允许
```

稳定的 `approvalId` 不能直接等同于 `toolCallId`:一个长命令或 shell bridge 可能在同一工具调用中产生多次审批。

断线重连后,只有仍未解决、并且服务端仍保存着回答入口的请求才能重放。客户端回答必须带原 request id;同一个回答重复到达时,服务端只能处理一次。

三个实现在这里也分出了差距:有的会用同一请求标识重放尚未回答的审批;有的断线后不保留回答入口,不能承诺恢复原弹窗;有的会主动撤回已失效的交互请求。自建时,这一格的差异要在断线场景里专门测。

第 19 章会把这些状态落到前端的状态更新函数中。

## 13.6 只限制文件写入还会漏掉什么?

前三档词汇主要描述**文件读写权限**,但正式产品还要分别设置下面五项。只写 `workspace-write` 而不说明其他限制,用户很容易高估沙箱能做什么:

| 需要限制的对象 | 起步做法 | 常见问题 |
|---|---|---|
| 文件系统 | 源码只读或独立工作副本;只开放明确 writable roots | 把宿主 `$HOME`、`.git/hooks`、Docker socket 一起挂进去 |
| 网络 | 默认断网;按域名/协议/端口白名单放行 | 只禁公网 IP,却留下 DNS/SSRF、代理或本地元数据服务 |
| 凭证 | 由凭证服务按调用短期下发最少权限 | 继承完整环境变量,子进程顺手拿到云 key/npm token |
| 进程与设备 | 限制可见进程、IPC、设备和子进程树 | 文件隔离了,却能 attach 宿主进程或访问高权限 socket |
| 资源 | CPU、内存、磁盘、PID 数、输出和 wall clock 配额 | 死循环、fork bomb 或日志灌满磁盘仍能拖垮宿主 |

资源超限要返回明确的错误类型(`cpu_limit` / `memory_limit` / `disk_limit` / `deadline`),而不是统一伪装成“命令失败”;模型只有看到真实类别才能换方案。

服务端还要区分**保存任务状态**与**让进程一直存活**。把 Goal、日志、job manifest 和产物保存下来,不等于为了“可恢复”让一个无限权限的 shell 永远运行。服务重启时,先按第 14 章恢复记录和实际状态,再按本章规则重新检查权限。

如果再加一个辅助 LLM 审查器检查危险操作,它只应读取结构化的工具名、规范化参数、解析后的资源和风险标签,不要把主模型的自由文本“我保证这是安全的”当证据。审查器超时或连续失败时转人工或拒绝执行;不同模型互审可以增加一票意见,不能替代内核、确定性规则和审批。

::: tip 一份完整的沙箱声明
不要只展示 `workspace-write`;同时展示 `fs=workspace-write, network=deny, credentials=scoped, process=isolated, limits={cpu,memory,disk,pids,wall}`。权限界面说得越具体,用户越知道自己批准了什么。
:::

## 13.7 与后续运行时有关的两个补充

下面两点分别会在第 19 章的界面状态和第 18 章的故障处理部分继续展开。这里先说明它们不能越过安全边界。

**乐观 UI(先显示无副作用状态)**:界面可以先显示“正在检查读取 src/main.py…”,后台执行权限判断;通过后再真正运行,不通过则改为“等待确认”。先发生的只能是 UI 更新,不能提前读文件或启动命令;这不是“推测执行”副作用。

**并行失败要看依赖关系**:已经确认互不依赖的调用中,一个失败可以只报告该调用,不必取消其他调用。若后一个调用依赖前一个结果,则应停止或标记“因依赖失败未执行”,不能一律隔离(第 18 章展开)。

## 自建起步:怎样实现最小审批检查?

完整沙箱需要原生依赖,但**审批检查**(本章的人机协议部分)零依赖可实现。它依次按三步判断,每一步都刻意保守:

1. **不能完整理解的 Shell 字符串 → 人工审批或拒绝**。`; | & $() >` 只是部分例子;换行、重定向、变量展开、子 shell 和程序自身配置都会改变行为。命令解析只能帮助解释风险,不能证明安全。
2. **只有经过审计的具体调用才能免审批**。判断对象应包含可执行文件、子命令、全部参数、cwd、环境变量和允许访问的资源。例如 `pnpm test` 会执行仓库脚本,不能默认安全;`ls <path>` 可能读取敏感目录;`git diff` 也可能受 pager、external diff、attributes 和配置影响。不要仅凭命令名或字符串前缀放行。
3. **其余 → 人工审批;无人应答 = 拒绝执行**。无交互终端(如 headless/CI)时直接返回"需要人工审批但当前无交互终端",而不是默认放行。

把检查放在 Shell 工具外面,Agent 就能在执行前请求审批。字符串前缀白名单(`cmd.startsWith("git status")`)会被 `git status; echo bypass` 绕过。解析 AST/argv 可以改善提示,但程序还会读取配置、插件和脚本;最终仍需 OS 沙箱限制可访问资源。审批只负责询问用户,不负责强制边界。

## 【对比小结】

| | codex | grok-build | dsh |
|---|---|---|---|
| 沙箱粒度 | 每条命令单独套 | 进程启动一次性(不可逆) | 每次调用选择平台后端 |
| 档位 | 三档 + 网络旋钮 | 档位更细,支持自定义 | 三档,只管文件效果 |
| 命令分析 | 规则引擎 + AST 拆段,批准后可学回规则库 | AST 检查最多,解析失败转人工,可选 LLM 分类器 | 不分析命令文本,由所选平台后端限制 |
| 升级路径 | 独立扩权工具(turn/session 级) | 无单次提权(换命令重问;拒绝被记忆) | **原地升级重试一次**,allowed-once 仅本次生效 |
| 防提权细节 | 保护 .git/hooks | hooks 目录写保护 | 先限制再 exec;Windows ACL 仅部分限制 |

需要决定的是检查放在哪里。用户态分析(codex/grok)能在执行前说明风险、改善审批体验,但很难覆盖 shell 的所有组合写法;操作系统限制(dsh)不可被命令文本绕过,但只能在执行被拒后说明问题。高风险、强交互产品通常同时使用两层:分析代码决定是否询问用户,操作系统负责阻止越界;受控环境也可以只使用后者,减少实现和维护成本。

## 本章小结

- 私有数据、不可信内容和外部通信同时出现时风险最高;持久记忆还会让攻击跨会话延续
- 四种常见机制:Seatbelt、Landlock、seccomp,以及使用 namespace/mount 的 bwrap;它们不在同一抽象层,限制对象也不同
- read-only / workspace-write / danger-full-access 是本书用于比较的三类词汇;三家的实际 profile、平台后端和默认值并不相同
- 文件档位只是一个维度:网络、凭证、进程/设备与 CPU/内存/磁盘/PID/时间配额都要单独声明和限制
- 命令可以先分析再交给沙箱(codex/grok),也可以主要依靠内核拒绝越界(dsh);是否叠加取决于风险和审批 UX
- dsh 的单次额外权限申请要求权限严格变宽、参数成对、`allowed-once` 只作用一次,被拒后不再自动绕行
- 黑名单不能保证安全;AST 分析可以帮助审批,真正的访问边界要由正确配置的 OS 沙箱强制。UI 可以先显示检查状态,但不能在批准前试跑有副作用的命令

沙箱和审批只能处理当下的操作。如果程序在审批后、工具启动后或结果写入前崩溃,系统还要判断操作是否已经发生、能否重试。下一章讨论怎样记录这些状态并安全恢复会话。
