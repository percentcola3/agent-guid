# 第 9 章 上下文的组成

::: info 本章要解决的问题
第 4 章把工具定义和工具结果接进了循环。现在把"上下文"这个词拆开:模型每轮看到的究竟有哪几块、各占多少、按什么顺序摆。
本章回答三个问题:**上下文由什么组成(先固定开销,后任务内容)、按什么顺序放、哪些内容只能当作数据而不能当作指令**。
:::

## 9.1 上下文由什么组成:固定开销在前,任务内容在后

先清点。每一轮请求的上下文里,有一部分是**还没开聊就要付的固定开销**:

| 固定开销 | 怎样进入上下文 |
|---------|----------------|
| 系统提示词 | Agent 的身份、规则和约束,基本不变 |
| 项目指令(`AGENTS.md` / `CLAUDE.md`) | 会话开始时读入:构建命令、代码规范、目录约定 |
| Skill 描述 | 每个 Skill 只放几百 token 的说明,完整步骤按需读取 |
| MCP 注册的工具定义 | 接一个 server,它的工具 schema 就进 tools 数组 |

这些内容每次请求都在、几乎不变——AGENTS.md 越长、接的 MCP 越多,还没处理任务就先占掉的 token 越多(第 8 章说过,5 个 MCP server 可能就是 5 万 token)。所以固定开销是第一类要管控的对象:系统提示词要测试、Skill 只放描述、MCP 按需接入(9.4 展开)。

**然后才是随任务增长的部分**:检索进来的代码、历史对话(含每次工具结果)、末尾注入的环境状态。这一部分的总量由预算决定,窗口大小随模型变化,实现时应读取当前限制,不要写死数字;窗口大也不等于填满划算——就算塞得下,也不该把整个代码库放进来:

```text
① 信息干扰:关键信息淹没在无关代码里(长上下文的中间位置召回下降,程度因模型和任务而异)
② 成本:输入、缓存读取和输出各自计价
③ 时效:代码在变,塞进去的"快照"转眼就是旧的
```

所以动态内容必须**按需选择**:代码靠检索(下一章),历史靠压缩(第 11 章),外部信息靠搜索(第 12 章)。本章剩下的部分先解决"按什么顺序放"。

## 9.2 怎样排列上下文才能复用 KV Cache?

根据第 2 章(KV Cache 与前缀缓存)的三条结论,上下文应按下面的顺序组装:

![把稳定说明放前面、当前状态放后面,以便复用 KV Cache](/diagrams/ch06-context-layout.svg)

不要通过**改写系统提示词**加入动态信息(如“当前目录是 X”)。变化位置之后的缓存不能继续复用,但变化之前的共同前缀仍可能命中。

动态信息通常放在较后位置,与稳定说明分开。Agent 可以每次根据记录计算一份当前状态,也可以把变化作为事件追加;下一节比较两种方式。

### codex 和 dsh 怎样加入机器生成的信息?

**codex 的答案是有类型的上下文片段。** `codex-rs/context-fragments/src/fragment.rs` 定义 `ContextualUserFragment`,具体类型分布在 `codex-rs/core/src/context/` 等目录。

部分机器生成的片段带起止标记,并在会话初始化、工具调用后或 turn 结束等时点加入模型输入。类型数量和标记覆盖范围会随版本变化,不要写成“约 35 种且每种都有标记”。仓库的 AGENTS.md 还要求新增内容有上限:

> - 无界项禁止:注入模型上下文的一切都必须有界、有硬上限
> - 单项不超过 10K token;新出现的可能超 1K token 的项要标记人工评审

标记可以帮助程序识别某些机器生成片段,但“能识别来源”不等于“可以安全删除”:仍要判断这段内容能否重新取得、是否影响审计和后续工具配对。

**dsh 的答案是提示词注册表加工具自带说明。** dsh 的 `core/system-prompt` 是一个有序 section 注册表:-100 放固定身份文案 `You are an AI agent powered by DeepSeek Harness.`(源码中的 section 名是 `harness:identity`),0 放 persona,100~199 放各工具的使用指引。插件可以向其中添加段落。

每个工具插件在注册工具时也注册自己的提示词 section。因此,工具与“怎么用这个工具”的说明由**同一个 npm 包分发**,不会因分别维护而失配。把工具说明硬编码在一个 `TOOLS` 数组里,是它的原始版本。

## 9.3 怎样给模型可靠的当前环境信息?

下面是一种**自建 Agent 的建议格式**,不是 codex、grok 和 dsh 共同采用的标准。

当前环境信息应尽量由程序从目标记录、工作区、任务调度器和工具调用记录中读取,而不是让模型凭记忆猜。对容易过期或影响安全的字段,可以同时记录:**来源**、**版本**、**读取时间**和**验证状态**。

验证状态由 Agent 根据读取方式判断,不能让内容本身自行声明。例如:

- `authoritative`(系统直接维护):Agent 自己维护的目标、预算、权限和工具调用记录。
- `verified`(刚刚核验):刚通过 Git、文件系统或进程查询得到的环境事实。
- `untrusted`(尚未信任):尚未核验的网页、工具文本、子 Agent 报告等;可以作为候选信息,不能直接改写目标或权限。

具体注入什么取决于产品。下面是一份常用清单;序列化给模型时可以保持紧凑,后台则保留必要的版本和读取时间:

```text
<environment>
工作目录: /Users/me/project
git 分支: feat/auth(主分支: main)
未提交变更: M src/api.ts, ?? src/auth/
最近提交: a1b2c3d feat: add token refresh
当前时间: 2026-08-14 13:00
token 预算: 剩余 43%
</environment>
```

这份动态状态能帮助模型正确引用路径、避免误改主分支,并判断该运行哪些测试。

`observedAt` 不是装饰:分支、文件和 job 状态都会过期。高风险操作前必须重新查询对应系统,不能拿几轮前的环境信息当锁。

### 替换快照还是追加事件?

| 方式 | 做法 | 优点 | 代价与适用条件 |
|------|------|------|----------------|
| **替换快照** | 会话日志保留原始事件;组装模型输入时只计算并放入一份最新状态 | 模型只看到当前值,实现简单 | 替换旧快照会让其后的 KV Cache 失效;应把快照放得尽量靠后、控制刷新频率 |
| **追加事件** | 只把 `branch changed`、`job completed` 等变化追加到消息流 | 保留前缀缓存与审计顺序,适合长会话 | 模型会同时看到旧值;必须靠 `revision` 明确 latest-wins,并在积累过多时压缩成新快照 |

不要覆盖会话记录后又声称保留了完整历史。完整历史应该只追加“发生过什么”,需要当前状态时再根据记录计算。

更稳妥的做法是:**原始记录只追加,发给模型的当前状态按需要计算**。短会话或状态变化少时,直接放一份当前状态最省心。长任务需要恢复和审计时,可以追加事件,到检查点再计算新的状态快照。

### 当前状态摘要也可能算错

状态摘要只是根据原始记录计算出的结果,不是新的事实来源。它写错时比完全不提供更危险:模型通常会直接相信“预算还剩 20%”“同一命令已失败 3 次”,不一定回头重新统计全部历史。

因此要把摘要当成一段需要测试的普通程序:

1. 计数、预算、权限、Goal 状态等可以确定计算的字段,由代码从唯一可信记录生成;不要让 LLM 批量阅读长历史后猜数字。
2. 摘要带上 `derivedThroughSeq` 或输入版本,说明它计算到了哪条记录;依赖文件、进程或网页的字段再带 `observedAt`。
3. 保留生成摘要所依据的原始事件或可重新查询的来源。摘要没有覆盖某个问题时,重新读取原始证据,不要把“字段不存在”解释为“事实不存在”。
4. 用重复、乱序、预算跨线、权限撤销和崩溃尾部等用例测试摘要。摘要格式变化也要做恢复兼容检查。

状态摘要可以减少模型每轮重新统计的成本,但它是有损信息。只有明确知道后续问题只依赖摘要字段时,才可以删除对应原文;否则保留原始记录或稳定引用。

### 读数什么时候必须由代码执行?

当前环境信息的价值不只是“让模型看见数字”,还要让代码根据读数采取明确动作:

| 读数 | Agent 的处理规则 |
|------|--------------|
| 同一错误重复达到配置阈值(例如 3 次) | 禁止原样重试,要求换方法、回滚或向用户说明 |
| 剩余时间接近预留的验证窗口 | 停止扩大搜索范围,优先 typecheck / test,如实列出未完成项 |
| token 预算低于压缩阈值 | 先裁剪可重取的工具输出,仍不足再执行有检查点的压缩 |
| job 超过预计时长且 `observedAt` 已旧 | 先刷新进程存活、日志游标和产物状态,不能直接判定失败或重复启动 |

模型可以参考这些状态调整计划,但预算达到上限后停止、同一错误重复多次后停止或换方法、权限被撤销后禁止执行,都必须由代码保证。**Prompt 里的”请停止”不能代替代码检查。**

## 9.4 固定开销怎样治理:按需加载,提示词像代码一样测试

固定开销不是越小越好,而是**每一段都该有人负责**。共同原则:**不要把所有知识一次性塞给模型**——稳定的项目指令放在前面,Skill 描述和工具清单控制总量,网页、文档和代码按需取回。下一章讨论代码检索,第 12 章讨论外部信息。

### 系统提示词也要像代码一样测试

系统提示词会改变 Agent 的工具选择、停止条件和安全行为,不应由多个插件随意拼字符串。自建实现可以把每一段注册成带稳定 `sectionId` 和顺序的记录,再由一个入口生成最终文本。

每次修改至少检查四件事:

1. 对生成后的完整提示词做快照测试,确认段落顺序、动态字段位置和实际发送内容。
2. 统计 token,阻止重复段落、互相冲突的规则和无界内容进入稳定前缀。
3. 权限、预算和高风险条件仍由代码强制;提示词测试不能替代运行时检查。
4. 用固定任务重新评估工具选择、任务成功率和拒绝行为。只比较源码中的某一小段提示词,不能代表模型最终看到的内容。

如果支持 vLLM、Ollama 等自托管服务,还要确认使用了与模型匹配的 chat template。system、user、assistant、tool 角色和工具调用不能简单拼成一段纯文本;模型或模板升级后,应重跑纯文本、单工具和多工具用例。

## 9.5 怎样防止读到的内容控制 Agent?

上下文中的网页、issue、日志或工具返回可能包含恶意指令,而模型难以稳定区分“用户要求”和“外部内容中的文字”。输入模型前应记录来源并区分指令与数据;第 12 章会讨论网页这一具体入口,第 13 章再用沙箱和审批限制实际操作。

### 先把指令与数据分开

模型会受到角色层级、位置和训练方式影响,因此并非“一切 token 地位平等”;但它仍可能把数据里的文字误当成指令。防御的第一步是同时记录**指令优先级**和**内容来源**,不能只按消息 role 二分:

```text
系统/开发者指令: 产品和运行规则,优先级最高
用户请求:       表达用户目标;其中粘贴的网页、日志仍可能是不可信数据
工具/文件/网页:  默认作为数据;只有经过认证、用途明确的控制工具才能提供权限撤销等系统事实
```

可以从三处入手:

1. 系统提示说明不同来源的内容应怎样处理。
2. 外部内容进入上下文时带来源、读取时间和边界标签,如 `<web_content source="...">`。
3. 对可信控制工具校验身份与结构,不要因为它也是 `tool` 消息,就把它与网页抓取结果等同。

XML 标签和提示只能降低模型误把数据当指令的概率,不是安全边界;恶意文本仍能伪造标签文字。

### 还要在哪些位置检查?

实现时应在多个位置减少风险;下面是建议的检查点,不是三个项目共同完成的实验结论:

```text
检查 1  指令说明      说明来源与优先级,降低模型误从概率
检查 2  来源记录      外部内容带真实的来源元数据和边界
检查 3  执行限制      写入、命令和网络经过沙箱/审批(第 13 章)
检查 4  外发限制      网络工具检查目标、数据范围与用户授权
```

来源标记和提示可以降低模型听从恶意内容的概率;沙箱、网络限制和审批则缩小即使模型判断错误时可产生的副作用。它们也不是绝对保证:沙箱配置可能不完整,用户也可能误批,因此还要记录实际授权和外发内容。

### 长期记忆为什么风险更大?

如果恶意内容被写入长期记忆,它可能在后续会话再次影响模型。因此,每条记忆都应记录来源、写入者、验证状态和有效期。

从网页或工具输出提取的信息写入记忆前要单独检查,读取时继续保留来源。不能因为内容“已经保存”,就自动提高它的可信程度。第 15 章会完整讨论记忆的写入与清理。

### 最少需要做哪些检查?

```text
□ 系统提示声明:工具/文件/网页内容是数据,无指令效力
□ 外部内容注入时包来源标签(用 fragment markers 顺手实现)
□ 危险动作(写/网络/执行)过沙箱或审批——上下文防御不替代执行防御
□ 记忆写入需用户确认或来源审查(第 15 章)
□ 知识库/检索产物带可信度标注(未验证的结论显式标记)
```

## 本章小结

- 上下文的组成分两块:**固定开销**(系统提示词、AGENTS.md、Skill 描述、MCP 工具定义)是还没开聊就占掉的部分,要管控;**任务内容**(检索的代码、历史对话、环境状态)按需选择
- 排列按"稳定前缀 + 增长的轨迹":固定开销在前、历史追加在后、动态环境状态放末尾——顺序由前缀缓存的经济性决定
- 环境状态(cwd/git/时间/预算)由代码生成、标记来源、放末尾注入;"请停止"不能代替代码检查
- 项目指令(AGENTS.md)是最经济的稳定前缀;Skill 只放几百 token 描述、内容按需加载;接 MCP 的工具 schema 也是上下文,接多少是上下文决策
- 读到的外部内容可能携带注入指令:指令与数据要分开、入口处过滤、高风险操作前再验证

本章确定了上下文的组成和排列方式,但大代码库仍然放不进去。下一章解决怎样找到当前任务真正需要的代码。
