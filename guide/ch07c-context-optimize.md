# 第 11 章 上下文的压缩与缓存

::: info 本章要解决的问题
第 10 章让 Agent 按需读取代码，但每次 grep、read 和工具结果都会让会话历史继续增长。运行时间足够长时，上下文仍会接近模型上限。

本章回答三个问题：**先裁掉什么、什么时候生成摘要、怎样同时考虑任务状态和缓存成本**。

压缩只能整理已经取得的信息。代码库中没有的最新文档和 issue，要到下一章从外部获取。
:::

## 11.1 会话太长时应该先删什么、最后压缩什么?

长会话的必然结局:历史越滚越长,逼近窗口上限。解法是**压缩(compaction)**——但"压什么、留什么"有讲究:

不要等到请求已经超过窗口才处理。第 2 章的预算还要预留输出、工具结果和失败修复空间;当剩余空间不足以安全完成下一轮时,即使窗口尚未填满,也应该先裁剪或压缩。

**dsh 的完整方案**(`packages/compaction/`):

- **触发**:token 压力达窗口的 **80%**
- **动作**:把旧对话区间交给 LLM 摘要,**保留 16%**(或绝对值)的近期原文
- **恢复结果一致**:压缩开始、替换范围和结果都写入会话记录;程序重启后读取同一条记录,不会重新生成另一份摘要(第 14 章)

**摘要不是一句泛泛的“帮我总结一下”,而是一份能让下一个模型继续工作的固定格式交接文档。** dsh 的 summarizer(`compaction-basic/src/summarizer.ts`)要求 LLM 输出下面八节 Markdown,一节都不能少,顺序也不能改变:

```markdown
## Primary Request and Intent
- 用户最初以及后来补充的目标;精确措辞重要时保留原文

## Key Technical Concepts
- 当前任务涉及的技术、框架、设计方式和项目约定

## Files and Code
- 文件的准确路径、作用、关键修改或必要代码片段

## Errors and Fixes
- 遇到的错误、解决方法以及相关的用户反馈

## Pending Jobs
- 用户明确要求但尚未完成的工作

## Current Work
- 生成检查点时正在进行的具体工作

## Next Step
- 与用户最新要求直接相关的下一项动作;没有则写 (none)

## Critical Context
- 决策及其理由、限制、用户偏好、待确认问题和继续工作所需数据
```

### 摘要生成成功,不等于可以立即替换历史

上面的八节格式来自 dsh。自建实现还应检查摘要本身,特别是目标、未完成项、文件路径、工具调用与结果配对、仍在运行的 job,以及精确标识符是否保留。检查失败时继续使用旧历史或缩小压缩范围,不要把坏摘要设为新的唯一上下文。

为了避免程序在“摘要刚生成、历史尚未切换”时崩溃后得到两种状态,可以把切换拆成可恢复的步骤:

```text
1. 到达安全边界,记下待压缩范围、sourceHash 和当前事件序号
2. 追加 compaction/start 记录
3. 生成并检查摘要
4. 追加 compaction/result,保存 summaryHash 和覆盖范围
5. 只有 result 已完整写入后,后续请求才改用摘要 + 近期原文
```

恢复时只承认完整的 `result`;孤立的 `start` 表示上次压缩未提交,可以安全重做。摘要是模型可见历史的替代表示,原始事件仍按第 14 章的留存规则保存,不能在切换前先删除。

## 11.2 压缩为什么会降低后续缓存复用?

压缩减少后续输入 token,但会改变一部分历史,因此也会减少该位置之后的缓存复用。两者需要一起估算。

### 缓存为什么会失效?

回忆第 2 章:前缀缓存的前提是"**开头不变**"。而压缩干什么?**改写历史**——把旧对话区间替换成摘要。精确地说:摘要**插入点之前**的稳定前缀(系统提示/工具定义/更早的内容)仍可命中,**插入点之后**的旧内容缓存全部作废,必须重算:

```text
压缩前:  [系统提示|AGENTS|工具] [历史 80k token,缓存命中 ✓]
压缩后:  [系统提示|AGENTS|工具] [摘要 8k token,新内容] [保留的近期原文]
          └ 共同前缀仍可能命中 ┘  └ 从摘要开始重新计算;稳定后可形成新缓存 ┘
```

::: tip 源码中的一个重要细节
缓存变化发生在**压缩之后的主对话**上;而**生成摘要的辅助调用**可能复用压缩前的共同前缀。一次压缩因此包含两部分成本:生成摘要的调用,以及主对话从摘要插入点开始的重新计算。两者是否命中仍受 provider、模型、TTL、路由和长度门槛影响。
:::

一次压缩是否划算,取决于压缩后还会有多少轮、输入与缓存读取的实际价格、摘要质量,以及窗口是否已接近上限。若任务马上结束,生成摘要可能不值;若还要运行很多轮或不压缩就无法继续,收益通常更大。不要用固定折扣和示例 token 数代替实际计价。

dsh 把触发阈值设在 **0.8 而不是 0.95+**,体现的是“提早留出恢复余量”的选择。源码给出了参数,但不要把具体数字写成普适最优值。

保留 **16% 近期原文**的主要价值是任务连贯性,而不是缓存。最近的对话记录着改到哪里、还差什么,摘要失真时损失最大。缓存层面,这些近期原文同样位于摘要插入点之后,原来的缓存不能继续使用。

### 压缩前还可以做什么?

按“每减少一个 token 会丢多少信息”排序,可以依次使用下面这些处理方式:

```text
① 工具结果裁剪(dsh:>8192 code point → 头 4096 + 尾 1024)
   —— 减少信息,且该结果位置之后的旧缓存不能继续复用
② 一开始就把超限输出写入有上限的文件—— 模型输入只放摘要和可用路径
③ 会话 fork(从已有历史创建新会话)—— dsh 会复制选定前缀,不是自动获得空上下文;
   若要隔离上下文,可把范围明确的任务交给只接收任务说明的新子 Agent
④ compaction —— 用摘要替换旧历史;插入点之前的共同前缀仍可能命中
```

这不是固定顺序。已保存完整输出时可以先裁剪;需要保留完整会话含义时可以直接压缩;任务本身可以独立拆分时再考虑子 Agent。

每一步都要记录丢了什么、还能否重新取得。第 16 章让子 Agent 只返回结论和产物路径,也是为了减少主 Agent 的上下文增长。

### 什么时候压缩最不容易丢掉当前进度?

dsh 当前保留 16% 近期原文,并用 LLM 摘要更早的区间;具体比例不应直接照搬。

压缩还应尽量避开任务中途,因为摘要容易丢失改到哪里、还差什么、哪些假设已经验证等进行中状态。较安全的时机是一个需求完成或一次提交之后。

dsh 把压缩记为日志事件,并支持 `/compact` 手动触发。用户或负责调度的程序可以主动选择时机,而不是只依赖阈值。

::: tip 一句话总结
压缩会换来更短输入,同时使摘要位置之后的旧缓存失效。优先选择可确认重取的内容,尽量在任务阶段边界压缩,并给近期对话留足原文。
:::

## 本章小结

- 上下文满了的处理顺序:先裁剪可重取的工具输出,再考虑压缩;压缩过程要完整记录并保留检查点
- 压缩摘要要保留任务状态、关键决策及其理由、失败路径;标识符原样保留
- 压缩改写历史,替换点之后的缓存全部失效——省下的 token 可能以重算的形式赔回去;挑任务边界压缩、摘要请求重放前缀,都是在对冲这笔账

压缩可以控制已经取得的信息量,却不能补上代码库中不存在的最新文档、issue 和 changelog。下一章讨论怎样搜索和读取这些外部信息。
