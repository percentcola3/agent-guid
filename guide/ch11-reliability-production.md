# 第 18 章 可靠性、任务评估与上线准备

::: info 本章要解决的问题
第 17 章让 Agent 可以接入外部能力，也把网络、第三方进程、版本和权限故障带进了主流程。Demo 能跑，不等于产品能在这些故障下保持正确。

- 失败后什么时候能重试，什么时候必须停止或纠正？
- 长任务怎样跨压缩、断线和重启守住目标？
- 怎样证明任务真的完成，而不是只收到“完成”状态？
- 怎样用日志、评估、预算和缓存控制上线风险与成本？

本章最终给出一份从错误恢复到上线评估的生产检查清单。
:::

## 18.1 三类常见故障及处理方法

生产级 Agent 的三类高发故障,每类都有标准解法(三家实现均有印证):

### ① 输出中断:模型生成到一半被截断

长回答撞上 `max_tokens`,输出戛然而止——补丁写了一半,JSON 工具参数没闭合。这里把一次独立的请求尝试称为 `attempt`。恢复前先问:**这次尝试是否已经产生外部副作用?** 没有副作用时可以丢弃整个 attempt 后重采样;有副作用时必须先恢复工具状态,不能把“重试模型”当作回滚。可以按以下顺序处理:

```text
第 1 级:完整 attempt 尚未提交且没有副作用 → 丢弃并提高上限重采样
第 2 级:仅纯文本被截断 → 把已完成文本作为显式上下文,请求继续
第 3 级:工具参数/结构化输出被截断 → 不拼接半截 JSON,重新生成完整结构
第 4 级:恢复预算用尽或工具结果未知 → 停止并把原因暴露给用户
```

细节见功力:dsh 的 step 循环让插件依次处理 `agent/request-error` 事件,因此**每个插件都可以注册自己的恢复方法**(比如对特定错误码做特殊重试)。还有个反直觉的双重标准:产品模式可以用占位符修补损坏的消息结构,**训练数据收集模式则拒绝修补**——因为合成占位符会污染训练数据(产品宽容、训练严格)。

### ② 连接卡死:最危险的失败不是断,是"静默挂起"

流式 API 的陷阱:连接建立成功,数据流却停了——水管通着但不出水。SDK 的连接超时管不到这里。解法是增加一个**空闲超时监视器**(watchdog,俗称看门狗):

```text
记录最后一次收到数据的时间戳
每收到一个 chunk → 刷新时间戳
超过 N 秒无数据 → 判定卡死 → 主动 abort → 按错误类型重试、切换备用线路或停止
```

可推广的原则:**每个长连接都要能证明自己仍在收发数据,不能只检查连接是否建立**。本章末尾的“自建起步”会把它具体列成设计决定。

### ③ 状态循环:Agent 陷入重复

表现:反复读同一个文件、反复发同一个工具调用、验证者连续指出相同缺口、上下文溢出后钩子又触发钩子。要分别处理:

- **轮次上限**(第 4 章要点三:循环必须带 `i < 20` 这类上限)——达到上限后必须停止
- **重复检测**:相邻两轮工具调用完全相同 → 注入提醒或强制中断
- **钩子死循环防护**(一个真实案例):上下文溢出导致 Agent 停止 → 触发“结束时自动提交”钩子 → 钩子调 LLM 写 commit message → 再次溢出 → 再触发钩子……解法:**递归深度计数器**,当前任务记录已经不完整时不再触发钩子
- **错误签名去重**:对 `(错误类型,工具名,规范化参数,验证缺口)` 做指纹;相同指纹连续出现且没有新证据,不要继续原方案
- **四类恢复各有上限**:传输重试、参数纠错、验证返工、重复保护不能共用一个模糊的 `maxRetries`

dsh 的会话日志也解决了另一个容易混淆的问题:崩溃后它不是简单“截到最后一个完整 turn”。已经完整写入的崩溃尾部会保留;恢复器会为已经开始但没有结束的工具、step 和 turn 追加确定的结束事件。尤其要区分:

```text
tool request 已记录,tool/start 未记录 → TOOL_NOT_STARTED,若仍需要可重新调度
tool/start 已记录,tool/result 未记录 → TOOL_OUTCOME_UNKNOWN,先查外部状态,禁止盲重试
```

这两个状态看起来只差一条事件,后续处理却完全相反。

### 先判断错误是否值得重试

前面的故障分类回答了"错误长什么样";这一节回答"错误来了怎么办"。天真的实现是"所有失败都重试三次"——直到你发现有些错误**重试必然再失败**,白白烧掉预算;有些错误**重试等于重复付费**。重试决策要过三问:

```text
问 1:这是谁的错?    传输层(网络/服务端)/ 模型行为(截断/坏参数)/ 系统 bug(自己代码)
问 2:重试会变好吗?  瞬态故障(重试可能成功) vs 确定性失败(同样输入必然同样输出)
问 3:重试安全吗?    幂等性(4.5.3)——LLM 调用安全,带副作用的工具调用不一定
```

grok 的重试实现(`xai-grok-sampler/src/retry.rs`)是三问答案的范本——它给**每类错误**单独标了 `is_retryable`,而不是一个全局策略:

| 错误类型 | 可重试? | 理由(源码注释原意) |
|---------|--------|---------------------|
| 空响应 / 流中断 / 流错误 | ✅ | 瞬态,预算默认 **14 次**,指数退避+抖动,含 HTTP/2→1.1 客户端重建 |
| **max_tokens 截断** | ❌ **刻意不重试** | "重采样同样的 max_tokens 只会再截断"——先修上限,再谈重试 |
| **响应解析失败(Serialization)** | ❌ | 确定性失败,防止烧完 14 次预算反复撞同一堵墙 |
| 推理死循环(DoomLoop) | 🔄 换法重采样 | 重试无意义,**换参数**重采样才有意义 |
| 413/图片超限 | 🔄 减少输入后重试 | 剥掉图片再试(改输入,不是原样重试) |

注意表格里的三种做法:原样重试(瞬态故障)、**修复后重试**(先修 max_tokens)、**减少输入后重试**(剥图)——后两种会先改变输入,这样下一次才有可能变好。dsh 则让插件依次处理 `agent/request-error` 事件,不同插件可以为特定错误码注册恢复方法,按顺序尝试(也是 18.1① 的机制基础)。

生产实现还需要三个教程常漏的限制:

- 尊重服务端 `Retry-After`,退避等待必须可被 `AbortSignal` 取消
- SDK、provider、Agent loop、MCP 各自重试时,共享一个父级截止时间和成本预算,避免重试次数相乘
- 每个 attempt 有独立 ID;失败 attempt 的流式文本只能标记为失败或替换,不能和下一次输出拼成一条消息

::: tip 根据错误类型决定是否重试
```text
429/部分 5xx/断流   → 结合服务端提示和本地错误分类;允许时退避重试,并受总截止时间与预算限制
连接/空闲超时       → 先分清发生阶段和副作用;只有被判为瞬态且可安全重放时才重试
max_tokens 截断     → 不用相同输入和上限原样重试;调整上限/输入或采用安全的续写方式,并记录新 attempt
解析/参数校验失败    → 不重试;错误回传模型自纠(4.4.5)
认证/配额/余额      → 不重试;立即上报用户(fail fast)
工具执行失败        → 回传模型;仅幂等工具可自动重试(4.5.3)
工具结果未知        → 不重试;先查询外部状态或请求用户确认
```
:::

## 18.2 Agent 如何根据失败自动改正

“纠错”不是一条 `while (!done)`。生产系统至少要分别处理四类情况,它们的触发条件、允许动作和停止条件都不同:

| 情况 | 何时触发 | 正确动作 | 主要风险 |
|------|----------|----------|----------|
| 网络请求失败 | 429、5xx、断流、空闲超时 | 同请求退避重试或切备用线路 | SDK、provider、Agent 各自重试,次数相乘 |
| 参数或方案错误 | schema 错、工具参数错、写入版本已过期 | 把结构化错误回给模型,重读后修参数或方案 | 把确定性失败当瞬态故障 |
| 验证后返工 | 编译、测试、e2e 或独立审查不通过 | 带证据返工,必要时重新规划 | 修改测试来骗过验证 |
| 重复保护 | 相同调用、错误或缺口反复出现 | 换策略、暂停、阻塞或请求人介入 | “继续努力”式烧预算 |

统一控制流程可以写成:

```text
发现问题
  → 判断错误类型、能否重试、是否已经产生副作用
  → 选择动作(retry / repair / reread / replan / rollback / inspect / escalate)
  → 保存证据(command, exitCode, diff, artifact, verifierVerdict)
  → 扣减 attempt / round / token / time / cost 预算
  → 进入 completed / blocked / paused / budget_limited / infra_paused
```

每次纠错都要留下稳定的 `attemptId`、错误指纹和新证据。若下一轮没有新证据、错误指纹也没变,继续原动作没有意义。

### 优先使用能自动检查的证据

```text
弱 ← 类型检查 < lint < 单元测试 < 集成/e2e < 独立审查者 < 人 → 强
      (快、确定)                         (慢、贵、接近真实目标)
```

同一个模型“再想一遍”容易复现原盲点;编译器、测试和真实产物不关心模型的自信。投入顺序应是:**先建立可自动执行的检查,再增加审查模型和提示词**。

独立审查有三种常见做法:

- **同一 Agent 自审**:最便宜,但作者与审查者共享上下文和盲点
- **另开上下文的审查 Agent**:只拿目标、diff 和验证证据,不继承生成过程中的自我辩护
- **只读的审查 Agent**:除另开上下文外,再用只读沙箱和权限限制,禁止它顺手改产物。codex 的 `guardian` 是这种做法在**危险操作和审批审查**上的例子,但它不负责判断 Goal(跨多轮保存的长期目标)是否完成

grok 的 Goal 新路径更进一步:实现者完成一轮后,由 `evaluator` 和多个 `skeptic verifier` 重新检查目标,`NotAchieved` 的 gaps 会交给下一轮继续修;相同 gap 指纹连续出现则进入 `NoProgressPaused`。这些名称来自源码,但不要把机制写成“任何 Grok 任务都必须通过审查 Agent”:

- 审查 Agent 受 Goal 模式和配置开关控制;关闭 `classifier` 时存在 `CompletedWithoutClassifier`
- 普通 Agent 只有声明 `completion_requirement` 才进入对应的 completion recovery
- legacy Goal 路径仍存在,并有验证基础设施故障后 `FailOpenAchieved` 的分支

所以生产设计必须明确选择:**验证不可用时停止并等待恢复,还是带着风险标记继续**。高风险代码修改建议进入 `infra_paused`,而不是把“验证器挂了”解释为“目标完成了”。

### provider、Agent loop 和审查 Agent 必须共享总预算

假设 provider 可重试 5 次、Agent 最多 64 轮、每轮 3 个审查 Agent,如果它们只管自己的上限,最坏调用量不是 64,而是成百上千。建议从 Goal 总预算中逐级分配:

```text
GoalBudget(token/time/cost/deadline)
├─ TurnBudget(maxTurns)
│  ├─ ProviderBudget(maxAttempts)
│  ├─ ToolBudget(maxCalls/perToolTimeout)
│  └─ VerificationBudget(maxRounds/maxReviewers)
└─ BackgroundBudget(maxJobs/maxRuntime/maxOutput)
```

子预算只能消费父预算,不能自行续杯。达到不同边界时保留不同停止状态:

| 状态 | 含义 | 能否自动继续 |
|------|------|--------------|
| `paused` | 用户主动暂停 | 否,等待用户 resume |
| `blocked` | 缺少输入/权限/外部条件 | 否,条件变化后再评估 |
| `infra_paused` | provider、验证器或执行设施故障 | 否,设施恢复后显式续跑 |
| `usage_limited` | 账号/速率限制 | 否,限制解除后再启动 |
| `budget_limited` | 本 Goal 的 token/time/cost 用尽 | 否,需提高预算或缩小目标 |
| `complete` | 验收条件已有证据 | 最终状态,不会自动继续 |

不要把"本轮停止"写成"目标完成",也不要用一个 `error` 覆盖所有可恢复状态。

### 保存完成依据:`complete` 状态本身不是证据

`status = complete` 只是一次状态变更。可靠实现还应保存一份完成依据,把完成结论绑定到目标版本和验证证据。字段不必照抄,但要能回答四个追问:

| 追问 | 建议记录(示意) |
|---|---|
| 验证的是**哪个目标版本** | `goalId + goalRevision`——目标被编辑后 revision 改变,旧完成依据自动失效 |
| 跑了**什么** | 命令清单(命令 + 退出码 + 输出引用) |
| 看了**什么产物** | 逐条 requirement 的裁决(`pass`/`waived` + 证据引用)、reviewedDiff、artifacts |
| 谁做了**最终判定** | 检查者的类型与身份:固定规则 / agent / human |

这份记录不是为了堆字段,而是把“完成”从一句模型自述,变成可以检查、并会随目标版本变化而失效的一组证据。

### 修复后怎样一步步证明故障已经消失

```text
第 1 步  复现优先
         修改前先得到稳定失败的测试/脚本/输入,记录原始现象。
第 2 步  证明原故障消失
         同一复现路径在修复后通过;flaky 场景要重复运行并记录次数。
第 3 步  按影响范围扩大回归测试
         类型检查/lint → 受影响模块测试 → 按改动范围选择全量/e2e。
第 4 步  保存证据
         保存命令、退出码、关键输出、diff/产物引用和目标 revision。
```

会话事件日志能保存工具调用和结果,但证据不会因此“天然可靠”:还要保证关键结果确实写入长期保存的日志、超长输出有稳定引用、系统能从这些记录重建状态,并且证据绑定正确的目标版本。

### 防止"把测试改绿"

模型可能通过削弱断言、加 skip、删除失败用例来获得绿色结果。防御清单:

```text
① 测试 diff 必审:新增断言通常合理,删除/放宽断言必须解释
② 复现用例不可撤:修改前失败的用例在最终变更中仍存在且启用
③ CI 统计新增 skip/xfail,超过基线直接失败
④ 测试目录可设为敏感路径,高风险任务需人工批准
⑤ 保留真实产物通道:例如真正渲染页面/文档后检查,而不只测生成代码
⑥ 审查 Agent 只读:不能一边判卷一边改答案
```

最后,失败的任务记录本身也是改进 Agent 的依据。按错误指纹统计参数或方案修正次数、审查 Agent 的拒绝原因、重复保护触发点和人工改写率,才能知道该改工具、约束还是提示词。

## 18.3 长任务如何持续记住目标

任务一长,Agent 不只会"忘记目标",还会发生状态覆盖、自动续跑旧目标、预算失控和恢复后重复副作用。第一步是把四个经常混用的对象拆开:

在保存 Plan 之前,先决定这项任务是否值得进入正式规划流程。计划不是越多越安全;对一个单文件文案修正写十步计划,只会制造陈旧状态。可以这样判断:

| 任务形态 | 推荐流程 | 为什么 |
|---|---|---|
| 单文件、边界明确、可快速回滚 | 直接探索 → 修改 → 验证 | 计划成本可能高于任务本身 |
| 跨模块、需求仍有歧义、会改变 API/状态模型 | 先澄清 → 形成计划文档 → 再执行 | 需要先固定边界、依赖与验收 |
| 架构迁移、数据变更或难以撤销 | 设计文档 → 人工批准 → 分阶段保存恢复信息 | 不能让模型边探索边扩大影响面 |

前端任务的计划文档(Plan artifact)不应只列文件名,至少写清页面入口、组件/store/API 边界、loading/empty/error 状态、兼容面和验证方式。目标明确但不可自动验证的任务,速度会受人工审查限制;目标模糊但自动验证很强更危险——Agent 会**高效地把错误目标做完**。当目标与验收都不清楚时,正确动作是补需求,不是增加轮数。

| 对象 | 回答的问题 | 保存多久 | 能否作为执行依据 |
|------|------------|----------|----------|
| Goal | 最终要达到什么、验收条件是什么 | 跨 turn、压缩和进程重启 | 是 |
| Plan mode | 当前是否只允许规划、是否禁止执行/编辑 | 通常是当前会话模式 | 是(控制策略) |
| 计划文档(Plan artifact) | 具体准备怎么做,依赖与验证步骤是什么 | 可版本化、可审查 | 是(执行依据) |
| Todo/progress | 现在做到哪一步,接下来做什么 | 高频更新,可由 Goal/Plan 重建 | 否,是根据目标和计划算出的临时状态 |

`update_plan`、`todo_write` 不是 Goal。codex 的 `update_plan` 约束同一时刻至多一个 `in_progress`;dsh 的 todo 是写入会话的整表快照,但下一次 `turn/start` 会清空这份临时进度。它们适合保持当前焦点,不能独自承担跨重启目标。

### 三家的 Goal 解法

| | codex | grok-build | dsh |
|---|---|---|---|
| 持久状态 | State DB 中的 `ThreadGoal` | `goal/state.json` 中的 Goal 协调状态快照 | 会话日志中的 `goal/change` 全量事件 |
| 状态 | Active/Paused/Blocked/UsageLimited/BudgetLimited/Complete | Active、多种 paused、Blocked/BudgetLimited/Complete,另有 Planning/Executing phase | active/paused/blocked/complete |
| 预算 | token budget + token/time usage | token budget、worker/verify 轮次、classifier cap | `maxGoalRounds` + `roundsStarted` |
| 并发保护 | Goal 状态锁 + `expected_goal_id`,避免外部更新与空闲时的自动续跑请求穿插 | `Mutex` 让 Goal 更新依次执行;重启时 Planning/Executing 回到 Idle,Active 改为 UserPaused,并清空子 Agent 记录 | `id + revision` 的 CAS(仅版本匹配时更新),旧引用返回 `GOAL_STALE_REVISION` |
| 进程重启后 | Active Goal 恢复后重新标记 active,空闲时可自动续跑 | Active 恢复为 `UserPaused`,Planning/Executing 归 Idle | 持久记录可保持 active,但进程内执行授权 `activation` 在 session start 时强制设为 `disarmed` |

最后一行体现了一个关键取舍:codex 倾向于恢复后继续追目标;grok 与 dsh 恢复已经保存的状态,但收回自动执行权。两种都合理,但教程必须把它写成**产品决策**,而不是把“会话恢复”自动等同于“任务继续”。

### 保存了目标状态,不等于允许继续执行

推荐单独保存一份**带过期时间的执行授权**,记录它允许执行哪个 `goalId + goalRevision`、由哪个当前进程或 runner 持有,以及一个**每次恢复都递增的执行授权版本号 `executionEpoch`**。恢复后只接受新版本号,旧进程的监视任务和自动续跑请求全部作废。

恢复长任务分两步:

1. 从日志/数据库重建 Goal、Plan、证据、预算和未完成工作
2. 重新取得执行授权,再决定是否发起下一 turn

第二步至少检查:Goal 的版本号 `revision` 是否仍匹配、用户是否追加或修正了要求、预算是否充足、上个工具的结果是否未知、工作区/模型/权限是否变化。没有执行授权时,`active` 只表示目标尚未完成,不表示当前进程可以执行有副作用的动作。

用户追加或修正要求时也必须检查并发版本。用户编辑目标后 `revision` 递增;已排队的自动续跑请求带着旧 `revision`,启动前发现不匹配就丢弃。

dsh 用 `GoalRef` 的 CAS(只在版本未变时更新)明确实现了这条规则。codex 用状态锁、预期 goal id 和推迟自动续跑,避免外部更新与空闲续跑交错。若自建多进程服务,还需要数据库 CAS 或唯一的执行授权记录,只有进程内互斥锁还不够。

### 长任务要保存哪些恢复信息

```text
created → planning → running
                    ↘ waiting_tool / waiting_user
                    ↘ paused / blocked / infra_paused
                    ↘ usage_limited / budget_limited
                    ↘ completed / failed / cancelled
```

不要只保存一个 `currentStep`。一份可用于恢复长任务的记录至少应包含:

```text
goalId + goalRevision + objective + acceptanceCriteria
planArtifactRef + planVersion + activeStep
completed/pending/blocked items
workspace baseline + changed files
pending jobs + outcome-unknown tools
latest verification evidence + proposed completion proof
token/time/cost/round budgets
last safe boundary + next action
```

恢复记录要在状态完整的节点写入:发 LLM 请求前、执行有副作用工具前、工具结果记入可信日志后、压缩完成后、turn 结束时。它不是另一份随意生成的摘要;字段应直接来自可信记录,并带 Goal revision。

### 压缩摘要不能决定 Goal 是否完成

压缩摘要可以告诉模型"目前发生了什么",不能决定 Goal 是否完成。正确关系是:

```text
持久保存的 Goal/Plan/Evidence ──按需读取──> 每轮动态注入
会话事件 ──有损压缩──> 模型历史摘要
```

压缩前后都从 Goal 服务重新读取 objective、验收条件、当前阶段、预算和下一步;摘要只引用 `goalRevision`,不要复制一份以后可能过期的目标。dsh 的 token-meter 会提示上下文还剩多少空间,但"何时压缩"与"是否继续 Goal"仍是两个决定。

分钟级任务可能一个 plan 就够;小时级任务至少需要持久保存的 Goal、恢复记录、明确的执行授权、逐级分配的预算和 18.2 的完成证据。

## 18.4 后台任务:活着不等于可恢复

第 7 章讨论了前后台执行模型;长任务还要面对**Agent 重启后的恢复**:内存里的 Promise、回调和 `AbortController` 都没了,外部进程却可能仍在运行。

一个 job 至少要保存以下信息:

- `jobId`、所属会话和轮次(`ownerSessionId + ownerTurnId`)
- 命令指纹与进程标识
- 状态(`starting / running / stopping / completed / failed / orphaned`)
- **输出读取位置**(`outputOffset`)与溢写文件路径
- 起止时间与退出码

**只有 PID 不够**:操作系统会复用 PID,至少要同时校验启动时间/进程组身份;容器或远程 runner 则应使用平台提供的 execution id。

### 进程重启后先核对记录和实际进程

| 持久记录 | 外部现实 | 恢复动作 |
|----------|----------|----------|
| running | 同一进程/runner 仍在 | 重新 attach,从 `outputOffset` 补读 |
| running | 进程已不存在 | 标记 `orphaned`,不得伪造 exit code |
| stopping | 进程仍在 | 继续 TERM→KILL 升级并等待整棵进程树退出 |
| completed | UI/模型没收到结果 | 重放结果,不重新执行命令 |
| 没有 start 记录 | 外部也没有执行证据 | 若仍需要,可以重新调度 |
| start 已记录,结果未知 | 外部状态无法查询 | 标记结果未知,请求检查或确认 |

dsh 的本地 subprocess 维护整棵进程树,输出通过单调 `nextOffset` 续读;当内存窗口已经滑走时返回 `lossy`。单路输出未超过 spill 上限时会提供文件路径;本地 bash/pwsh 的默认上限是 64 MiB,超过后删除 spill 文件,只保留内存尾部。

这能让当前进程持续读取子进程状态,不代表 daemon 重启后仍能重新 attach,也不保证任意大小的全文都可找回。产品能力表必须单独说明是否支持重启后恢复,以及能保留多少输出。

grok 的后台任务记录 `owner_session_id`,可以按 owner 列表、转移或取消任务;它还专门处理 wait 与 completion 同时发生时的通知丢失:只有真正拿到完成结果的 waiter 才能阻止自动唤醒,被取消或掉线的 waiter 不能让完成通知永久消失。这个时序问题值得自建实现直接照着测:

```text
等待者注册 → task 恰好完成 → 等待者被取消或连接断开
期望:结果要么由等待者收到,要么写入一条重启后仍可读取的唤醒事件;不能两边都没有
```

### 取消必须明确目标

`cancel()` 到底取消什么要写进 API,不要靠调用位置猜:

| 取消目标 | 典型行为 |
|-------|----------|
| attempt | 只取消当前 provider 请求,不结束 turn |
| tool-call | 终止该工具及其子进程树,记录 cancelled result |
| turn | 取消未启动工具和当前前台工作;后台 job 是否保留由策略决定 |
| job | 按 `jobId + ownerSessionId` 终止一个后台任务 |
| goal | disarm 自动续跑,并按策略取消该 Goal 拥有的 job/子 Agent |
| session | 停止该会话全部前台工作;不能误杀其他会话的共享任务 |

取消请求应幂等,迟到的完成事件仍要写入记录,但不能把已取消 Goal 自动唤醒。后台任务的实时输出与浏览器重连细节放到第 19 章。

## 18.5 如何提速,又不让一个失败拖垮整轮

第 3 章 3.5、第 4 章 4.5 和第 13 章 13.7 已分别介绍工具执行、并行和沙箱中的相关问题,这里列出三项相互影响的选择:

**执行时机**:流式输出下,"何时开始执行工具"各家选择不同——codex 在**单个输出项完成**时即可启动执行(不用等整条消息),dsh 则**等整个流组合成完整 assistant 消息后**才执行(实现简单、结果确定)。前者缩短用户从请求到结果的总等待时间,后者更容易实现、调试和复现。

**并行执行**:彼此独立的调用可以同时运行。dsh 要求每个工具通过 `isConcurrencySafe()` 声明是否允许并发;允许并发的调用最多同时运行 `maxParallelToolCalls` 个,不允许并发的调用必须单独执行,前后不能穿插其他工具。结果仍**按模型给出的顺序**提交,保证上下文稳定。abort 时给未启动的调用补一条合成错误结果,这样从日志恢复时消息结构仍然完整。

**失败彼此隔离**:独立调用互不中止,错误作为该调用自己的结果回传,不上抛终止整个 turn(第 13 章同样采用这条原则)。如果希望前一个调用失败时自动取消依赖它的调用,就必须显式记录调用间的依赖;三家的实现都以**互不连坐**为主,不会自动推断依赖图。

## 18.6 上线前还要补齐交互、配置、测试与模型选择

**交互形态**:codex 主打终端 TUI(+ headless 模式做 CI/脚本);grok 同为 TUI(+ ACP 协议嵌编辑器);dsh 反其道,主打 **Web UI**(浏览器是它的第一公民,CLI 只是启动器)。三种形态对应三类用户,没有优劣——但 dsh 用 Web 形态换来了审批 UI、diff 卡片这类富交互的天然优势(第 13 章的审批、第 6 章的编辑 diff 卡片都长在 Web 上)。

**配置体系**:多级配置(用户级/项目级/命令行)是标配;codex 甚至为配置生成 JSON Schema(可由程序校验的数据结构说明,见 `config.schema.json`);dsh 的配置即 YAML 插件清单(第 17 章)。

**了解系统正在发生什么**要靠日志、指标和调用追踪。这些数据不能和会话恢复记录混为一谈,至少要分别记录三类:

```text
会话可信记录  模型消息、工具调用/结果、Goal 变化;用于恢复与一般审计
运行指标      延迟、token、缓存命中、错误率;允许采样和丢失
安全审计记录  审批、提权、敏感路径/网络访问;使用独立留存策略
```

codex 分别写 rollout 与 otel/analytics;grok 把 `updates.jsonl` 作为会话的可信记录,`events.jsonl` 只尽力写入,失败可以丢弃;dsh 也把会话事件与根据事件计算 token 用量的 token-meter 分开。运行指标写失败不应阻断 Agent;会话可信记录写入失败时,继续执行有副作用的动作之前必须停止。

最小字段也不只是一行 token 账单。三条流都应带可关联的 `sessionId/turnId/stepId/attemptId/toolCallId/jobId/goalId+revision`,再记录模型、耗时、输入/输出/缓存 token、重试分类、停止原因和证据引用。这样才能从"一次调用贵"追到"哪个 Goal 的哪次纠错烧掉了预算"。

### 用主动制造故障来测试恢复能力

可靠性不能只靠线上日志。准备一个**输出固定的假模型服务**、一个能统计执行次数的假工具(分别模拟可安全重复执行与不可安全重复执行),然后在每个写入持久记录的前后主动崩溃,形成三组回归测试:

| 套件 | 注入场景 | 必须断言 |
|------|----------|----------|
| 恢复 | tool/start 前后、result 写入磁盘前后、compaction 中途、进程重启 | transcript 结构合法;已保存的结果只读取记录、不重新执行;未知结果不盲目重试;有外部影响的操作不重复执行 |
| 自动改正 | 429、坏参数、相同测试失败、审查 Agent 不可用、重复 gap | 四类情况采用正确处理方式;共享截止时间生效;最终停止原因准确;不会把基础设施故障标成 complete |
| 长任务和后台 job | 两次压缩后重启、Goal 被人工修改、wait/completion 同时发生、进程消失 | 继续使用最新版 Goal/验收条件;旧 `revision` 的自动续跑请求被丢弃;只唤醒一次;失联进程标为 orphaned |
| 模型服务适配 | 纯文本、单工具、多个工具乱序完成、文本与工具增量交错、参数只收到一半就断线 | 完成事件和 usage 只提交一次;工具按 ID 配对;半截参数不执行;失败 attempt 不与重试输出拼接 |

起步时先设三个最低通过条件:

```text
恢复正确性:所有 crash point 都通过,非幂等副作用重复数 = 0
重复错误停止率:同一错误达到次数上限后应 100% 停止或换方法,不得继续原动作
长任务连续性:经历 N 次压缩 + 重启后,goalRevision/验收条件/预算逐字段一致
```

真实模型只用于补充评估,不替代这套确定性回归;否则一次模型波动会掩盖真正的状态机 bug。

### Agent 应遵守哪些 git 操作规则

Agent 改了代码,就要回答 git 的三个问题:**何时提交、怎么写提交信息、哪些操作禁止**。生产约定:

```text
何时提交      默认:不主动提交——用户明确要求才 commit(codex 系与 Claude Code 系
              的系统提示都有此硬约定,防止 Agent 替用户做不可逆决定)。
              例外:内部检查点用隐藏引用,不进用户历史——grok 在 conv/* 隐藏分支上
              做"turn 结束若有脏文件就 add -A + commit"(--no-verify、禁 gpgsign、
              有进行中 git 操作则跳过),用户可见历史保持干净。
提交信息      LLM 从 diff 生成的总结,但结构上应是"建议+待确认",而非直接执行;
              默认分支上先开分支(codex 约定),push 永远要人点头。
禁止操作      强推、改历史、动保护分支、`git config` 全局篡改——第 13 章的
              危险命令特判里有专门针对 git 危险 flag 的拦截。
```

**设计原则**:git 的 commit/push 是**对外可见且难撤销**的动作,应按第 13 章的规则由人工确认;内部检查点(6.5 的文件快照、grok 的 conv/* 提交)则用于失败后恢复到旧状态,两者要分开。

### 根据任务难度和成本选择模型

Agent 可以由运行程序按任务难度选择模型:

```text
简单确定性任务(格式转换、读文件总结、生成 commit message)→ 小/快/便宜模型
复杂推理(根因定位、架构改动、跨文件重构)                → 强模型/思考模型
```

两个生产实现给出了不同佐证:

- codex 的 spawn_agent 指引明确“**子 Agent 默认继承当前模型,除非用户明确要求否则别设 model**”——模型选择是显式决策,不是随手参数
- dsh 允许插件依次处理 `agent/request`,按任务改写 provider/model,且每次变更记为 `request/header` 事件。模型切换会断开原有缓存,可用 18.8 排查表第 3 条追查

是否启用更长思考也属于模型选择,但不能靠“探索关、定案开”这类直觉写死;应按任务标签在本地任务质量评估中验证质量、延迟与成本。

给自建 Agent 的起步策略:**先不要自动选模型**——先全用一档模型把功能跑通,等 token-meter 与运行指标(18.6)告诉你“哪类调用最贵且最简单”,再只把那一类换成更便宜的模型。自动选择本身也会增加复杂度,要有数据再做。

## 18.7 任务质量评估:状态正确不等于任务做对

18.6 的故障注入回答的是“日志、重试、恢复有没有破坏既定规则”。它不能回答另一个更重要的问题:**Agent 最后是否真的解决了用户任务?** 评估对象不能只有模型,而要包含完整的 **Agent**:模型、上下文、工具、权限和验证方式都属于评估对象。同一个模型换了这些部分,表现就是另一套系统。

这里把任务质量评估简称为 **eval**。先把三种测试分开:

| 层 | 运行条件 | 回答的问题 | 典型用途 |
|---|---|---|---|
| 确定性可靠性回归 | 输出固定的假模型服务 + 故障注入 | 状态机和副作用处理会不会坏 | 每次提交必跑 |
| 离线任务质量 eval | 真实模型 + 可重置环境 + 固定版本 | 在目标任务分布上做得多好 | 模型/提示词/工具发布前 |
| 线上小流量试运行 | 少量真实流量 + 安全限制 + 快速回滚 | 离线收益能否迁移到真实用户 | 发布阶段 |

单元测试不能代替 eval;eval 的随机波动也不能代替单元测试。前者检查代码必须始终满足的规则,后者衡量模型这种概率系统的实际表现。

### 一道题必须包含任务、环境、限制和判定方法

Coding Agent 的每个用例都需要一个可重置的测试环境。一道 eval 题至少由五部分构成——**任务指令**、**固定起始环境**(初始 git commit / 容器镜像 / workspace snapshot)、**允许和禁止的动作**、**检查方法**与**预算**(轮数 / token / 成本 / 墙钟时间)。检查方法有三类,按客观程度排列:

| 检查类型 | 检查什么 | 例子 |
|---|---|---|
| command | 命令退出码 | `pnpm test` 期望 exit 0 |
| file | 文件内容条件 | `src/api.ts` 中不再出现 `console.log` |
| render | 真实渲染 + 评分规则 | 打开 `/checkout` 路由,按视觉规范评分 |

### 会提问的 Agent 还要用可交互用例测试

静态题只能验证“信息都给全后能不能完成”,测不出 Agent 是否会在信息不足时正确询问用户。可以用一个小状态机模拟用户:隐藏事实由测试脚本保存,Agent 问到对应问题时才返回脚本中的答案;没有问到就不能主动补充,更不能临时编造新信息。

这类用例除了最终产物,还要检查:是否询问了必需信息、是否在高风险动作前取得确认、是否带着错误假设继续执行,以及用了多少轮才问清。模拟用户和 Agent 操作同一份可重置环境,这样用户回答、工具结果和最终状态才能互相对应。

每次运行都从同一个固定起始环境开始,并尽量固定网络、依赖、时间和外部 API,或者用可控的假服务替代。修复类任务至少同时检查:

```text
FAIL_TO_PASS   原故障真的消失
PASS_TO_PASS   旧能力没有被破坏
workspace      用户原有 dirty changes 没丢、没被卷进提交
policy         没改测试期望、没新增 skip、没碰禁改文件
artifact       最终文件/页面/数据正确,而不是 Agent 自报“完成”
```

因此不要拿最终回复做字符串匹配。回复写得漂亮而代码没改对,仍然是失败;回复很短但产物、测试和约束全满足,就是成功。

### 能用确定规则检查,就不要先让 AI 打分

推荐按下面的顺序增加检查能力:

1. **确定性结果检查**:测试、类型、lint、退出码、文件内容、数据库状态。
2. **执行过程检查**:是否越权、绕过审批、重复副作用、改测试或消耗超预算。
3. **真实产物检查**:前端项目必须实际 build 并在浏览器渲染,采集 console error、DOM、a11y tree、截图和关键交互。
4. **AI 评审**:只处理可读性、视觉质量、解释质量等难以写成断言的方面。
5. **人工抽检**:校准 AI 评审,处理模糊需求和高风险边界。

负责视觉检查的 AI 不能只看源码;它至少要看到渲染后的截图、DOM 和 a11y 证据。生成方案的 Agent 与只读审查 Agent 要分开,再把结构化问题交回修改代码的 Agent,并限制返工次数。任何一层的基础设施故障都应标为 `evaluator_error/infra_paused`,不能算成 Agent 成功或失败。

AI 评审也不能只是“再找一个聪明模型凭感觉打分”。评分规则要拆成**必要项、加分项、一票否决项和边界例子**;数据外泄、虚构证据、越权操作这类严重问题不能被其他项目的高分抵消。为减少偏差:

- 隐去模型/方案名字,配对比较时交换左右顺序;
- AI 评审必须引用可观察证据,不评价隐藏思维链——第 1 章已说明 CoT 不是内部推理录像;
- 检查得分是否只是随回答长度一起上升,并在评分规则中明确“更长不等于更好”;
- 用一批人工标注样本校准 AI 评审,定期检查误判;
- 关键结论尽量用不同检查方法交叉验证,而不是让同一上下文自证。

### 测试集、指标与版本记录

测试集至少同时包含典型任务、边界任务、陷阱任务和“应该拒绝/无法完成”的任务;结果要按能力类型和难度分别统计,不要只报一个总分。生产失败可以变成回归用例,但要先脱敏、人工确认,并另存一份**从未参与开发调优的测试集**。改变文件名、路径和数据再重复出题,能减少系统只记住固定题面的风险。

测试题本身也有生命周期。至少保存 `caseId`、版本、来源、能力类别、难度、固定起始状态、检查程序版本和负责人,状态使用 `draft → validated → active → quarantined/retired`。含义不清、依赖不稳定或无法重现的题先隔离,不能继续混在总分里。生产失败只有在完成脱敏、复现和人工确认后才能进入回归集;开发调参集与从未用于调参的测试集应分开存放并控制访问。

最小指标分三组,不要揉成一个“综合分”:

| 组 | 最小指标 | 解释 |
|---|---|---|
| 结果 | 单次尝试成功率(Pass@1)、连续 k 次全通过率 | 前者看一次成功,后者看稳定性;不要用多次尝试中的“最好一次”掩盖波动 |
| 安全/路径 | 严重违规率、测试篡改率、重复副作用率 | 严重违规应一票否决 |
| 经济性 | 成功任务成本、端到端 p50/p95(中位数/95 分位)、轮数/工具数 | 便宜但不断失败重试的模型可能更贵 |

每次 eval 还要保存完整版本信息,否则分数变化后无法判断是哪项改动造成的:

```text
model/provider/version + reasoning config
Agent runtime commit + rendered system prompt hash + tool schema hash
AGENTS.md/memory snapshot hash + starting environment/image hash
eval case version + traceRef + budget + stop reason
```

### 一次任务怎样追到每个模型和工具步骤?

一次任务使用一个稳定的任务追踪编号(`traceId`);每个 turn、模型请求、检索、工具、后台 job 和子 Agent 再记录自己的步骤编号与父步骤编号。步骤只保存诊断所需的时长、状态、token/成本、错误分类和脱敏后的证据引用,不要默认复制全部 prompt、源码和工具输出。

错误、安全事件和高成本任务应完整保留必要记录;普通成功任务可以按策略抽样。跨子 Agent 传递同一个任务追踪编号,才能知道总成本和失败来自哪一支。运行追踪用于诊断和评估,不是第 14 章的会话事实来源;即使指标系统丢数据,也不能据此重新执行工具。

### 小幅提升可能只是随机波动

比较两版时让它们运行同一批题,逐题配对,并对有随机性的题重复运行。报告多次结果的范围,不要只挑最好的一次。当差异仍落在重复运行的正常波动内时,就没有证据支持切换。同时试了很多改动后出现的“最好一项”,还要在没有参与挑选的测试集上独立复跑。

做模型选型时固定其余 Agent 组件,只换模型;评估 Agent 的某项功能时固定模型,只替换或关闭一个组件。系统提示词、记忆、检索、压缩和 Skill 等主要能力最好有独立开关,使单项对照和快速回滚成为可能。每项实验同时看任务成功/返工等目标指标、该机制是否生效的过程指标,以及成本、延迟和安全这些不能恶化的指标;“检索命中变高”不能单独证明任务质量提升。

最终要看质量、稳定性、p95 和**每个成功任务成本之间的折中**,不是只选排行榜第一名。

### 评估通过后,再小流量发布

提示词、工具 schema、Skill 和验证用的评分规则都是**需要版本管理的发布内容**,不是线上可随意自改的字符串。一次失败记录只能产生一份待验证的改动:

```text
检查失败原因 → 待验证改动 → 回归测试 + 未参与调优的测试集 → 只改一个变量做对照
            → 线上小流量试运行 → 目标指标 + 安全指标 → 发布或回滚
```

先检查固定起始环境和检查程序是否坏了,再判断是不是 Agent 的问题。线上任务记录默认不全量收集敏感正文;保存脱敏后的字段、哈希、证据引用和必要抽样即可。只有经评估证明可以用于其他任务的经验,才进入第 15/17 章所讲的长期记忆、Skill、脚本或工具。

::: tip 一句话
可靠性回归证明“系统不会把账记乱”;任务质量 eval 证明“它把事做对了”。生产 Agent 两套都要。
:::

## 18.8 怎样保持缓存命中,降低延迟和成本

第 2 章讲了 KV Cache(模型复用相同输入前缀的计算结果)原理,第 9 章说明了为什么要把稳定说明放前面、当前状态放后面,11.2 讲了压缩的缓存代价。这里给出一份**可直接执行的检查清单**:先测量,再对照“哪些改动会断开缓存”逐条排查,最后用八条做法保持命中率。

### 先测三项数据

```text
1. 通过 provider 适配层读取缓存命中量。字段并不通用:例如 OpenAI Chat Completions
   可见 `prompt_tokens_details.cached_tokens`,Responses API 使用输入 token 明细,
   其他服务可能用不同字段或不返回该数据
2. A/B 验证:同一任务跑两版(改写系统提示词注入动态信息 vs 追加式注入),
   对比总成本与延迟——KV-cache 友好设计 + 压缩带来真实、可量化的节省,
   已有完整示范可循
3. 监控三条曲线:缓存命中率(应走高)、首 token 延迟、$/任务
   命中率突降 = 前缀被谁改了,通常是某个"好心"的动态注入
```

### 七类会让缓存失效的改动

前缀缓存失效通常由有限的几类改动造成。命中率下降时,按这张表逐项检查:

| # | 行为 | 代价 | 缓解 |
|---|------|------|------|
| 1 | 改写系统提示词(哪怕一个字) | 从变化位置开始的后续前缀不能继续命中;系统提示词靠前时通常等于大部分请求重算 | 系统提示词版本化,变更集中发布;动态信息追加到后面 |
| 2 | 工具列表/顺序/schema 变化 | 如果模型 API 把工具定义计入缓存前缀,变化位置之后需要重算 | 会话内保持定义和顺序稳定;只有协议明确支持延迟工具且不改写已有前缀时,`tool_search` 才可能保留更多命中机会 |
| 3 | **换模型** | 不同模型的缓存相互隔离 | 同会话锁定同模型;dsh 把 provider/model 变更记成 `request/header` 事件——可以查到是哪次切换导致缓存失效 |
| 4 | 压缩改写历史 | 11.2 的账:主对话前缀重建 | 在一个任务阶段完成后再压缩;摘要调用本身用 dsh 的“重放前缀+尾部指令”技巧保缓存 |
| 5 | 历史消息被编辑/重排 | 对应点之后全部作废 | 只追加,不重写(第 14 章的记录规则) |
| 6 | 重新打开会话/恢复/fork | 可能零命中 | 如果从日志重建出的请求前缀逐字相同,就保留了**命中机会**;但 provider 只尽力复用缓存、不作保证,模型、工具 schema、配置或压缩版本变化仍会断缓存 |
| 7 | 前缀没有达到服务的缓存条件 | 最低 token 数、保存时间和计费规则因 provider、模型与套餐而异 | 查当前服务文档并从 usage/延迟实测,不要把 1K 或其他数字写成通用阈值 |

### 保持缓存命中率的八条做法

```text
① 稳定内容永远在前:系统提示词 → AGENTS.md → 工具定义
② 系统提示词保持固定:不掺时间、计数器、随机数或当前环境信息
③ 一切动态信息(时间/git 状态/余量)走追加的尾巴,粒度放宽(时间到分)
④ 会话内尽量保持工具定义和顺序稳定;使用 tool_search 等延迟发现时,先确认当前模型 API 怎样把新工具加入请求、是否仍保留已有前缀的缓存机会
⑤ 历史只追加:改写历史 = 主动烧钱(修复需求交给下一轮,而非编辑上轮)
⑥ 换模型 = 显式事件:记录、审计、尽量少干
⑦ 压缩挑任务边界;压缩前后各看一眼命中率曲线,把 11.2 的账算进来
⑧ 每次发版比较系统提示词、工具列表和 AGENTS.md——
   任何一个变了,当天命中率曲线会告诉你代价
```

::: warning 一个真实的高发 bug
给系统提示词加时间戳(`当前时间:14:03:22`)——每秒都在作废缓存。正确做法:时间进**动态尾巴**(第 9 章状态栏),且粒度到分钟即可。
:::

::: tip 一句话
提高缓存命中率不需要更强的模型,关键是保持前缀内容和顺序稳定,并把每次变更纳入版本检查。
:::

## 自建起步:带看门狗的流式调用,七个设计决定

把 18.1 的三类故障和重试判断落成一个可靠的模型调用层,不需要多少代码,但有七个必须显式做出的设计决定。下面以 **OpenAI Chat Completions 风格的 SSE 适配器**为例;Responses API、Anthropic content blocks 和其他服务的事件名、工具增量字段与完成条件不同,要在适配层分别实现。

**① 连接超时与空闲看门狗是两回事。**
连接建立成功但数据流停了(水管通着不出水),SDK 的连接超时管不到——必须独立记录"最后一次收到数据的时间戳",每收到一个 chunk 刷新,超过阈值(如 30s)判定卡死,主动 abort 后按可重试处理。

**② 先收完整一个 attempt,再提交给调用方。**
流式增量只进 UI,不进最终结果。必须按当前 provider 的协议等到响应、item 或 content block 完整结束,并确认没有拒绝、截断或流错误,再把 assistant 消息(文本 + 工具调用)作为最终返回。

Chat Completions 的 `finish_reason` 只是判断依据之一,不是所有 API 的通用完成信号。否则截断的流会被当成成功、半截工具参数会进入执行器——这对应 4.4.2 的调用侧检查。

**③ SSE 帧与 UTF-8 都要跨 chunk 处理。**
一块网络数据可能包含半帧、一帧或十帧;解析器保留未闭合尾巴直到空行;解码器复用同一个 `TextDecoder` 并带 `{ stream: true }`,否则跨块的中文字符会变乱码(第 19 章展开)。

**④ 工具参数按调用标识拼接,流结束后才解析。**
在 Chat Completions 适配器里,`tool_calls` 增量通常按 `index` 对应并拼接 `arguments` 字符串;其他 API 可能用 item ID/content block index。只在对应调用完整结束后整体解析——这对应 4.4.3 的“收完整后再解析”规则。

**⑤ 按错误类别和服务端提示决定是否重试。**
不能写成“所有 429/5xx 都重试、所有其他 4xx 都不重试”。服务可能用响应头明确禁止重试;某些 5xx 是证书或配置等确定性错误;413 或图片处理错误则可能在减少输入后成功。

认证、配额和坏请求通常先交给上层处理。真正的瞬态错误才走指数退避 + 抖动,并按服务规则处理 `Retry-After`。grok 的实现还专门限制连续 429 次数,并排除 Cloudflare 525/526。

**⑥ 检查当前协议的截断信号。**
在 Chat Completions 中,`finish_reason == "length"` 表示 token 上限截断;其他 API 的字段不同。相同输入和上限原样重采样通常还会截断,应先提高上限、减少输入,或只在纯文本且边界明确时带着已完成内容续写。工具参数和结构化输出不要拼半截 JSON,应创建**新 attempt**重新生成完整结构。

**⑦ 重试不拼接输出。**
每次尝试有独立 `attemptId`;失败的 partial 只进 UI(标记中断),绝不能和下一次的输出拼成一条消息(4.5.4)。

对照 18.1,这些检查分别处理不同故障:

- 空闲超时监视器处理**卡死**
- 错误分类处理**网络和限流错误**
- provider 的完成与截断信号防止**把不完整输出当成功**
- 独立的 attempt 记录防止**把两次重试拼在一起**
- 轮次上限(第 4 章)处理**状态循环**

想读产品级实现,可对照 grok 的 `xai-grok-sampler/src/retry.rs`(逐类错误决定处理方式),以及 dsh 让插件依次处理 `agent/request-error` 的实现。

## 【对比小结】

- codex 选择更积极的 Goal 自动续跑,因此必须控制何时推迟续跑、剩余预算和副作用的幂等性
- grok 对完成验证最积极,同时也暴露了审查开关、旧实现路径,以及验证设施故障时“停止等待”还是“带风险继续”的真实取舍
- dsh 对持久化边界、Goal revision 和未知工具结果定义得最明确;代价是更多状态与恢复协议
- 三家都说明同一件事:**保存状态、证明完成、重新获得执行授权是三个独立问题**

## 本章小结

- **不同失败不能只用一个 retry 循环处理**:网络失败、参数或方案错误、验证返工和重复保护各有规则,但共享同一个 token/time/cost 总预算
- **完成状态不是完成证据**:完成依据要绑定 Goal revision、验收条件、命令、产物与检查者;验证设施不可用时要明确停止等待,还是标记风险后继续
- **Goal、Plan mode、计划文档和 Todo 必须分开**:Goal 跨压缩和重启,Todo 只是根据目标与计划算出的临时进度
- **保存状态不等于恢复执行权**:用带版本号的执行授权淘汰旧自动续跑请求;用户修改目标后通过 revision/CAS 防止旧请求覆盖新目标
- **崩溃恢复要看副作用状态**:`not started` 可以重新调度;结果未知时必须先查外部实际状态
- **后台任务要明确进程重启后的恢复规则**:保存 owner、进程身份和输出 offset;核对失联进程;避免等待者断开时丢完成通知;取消时明确目标
- **修复验证四步**:复现 → 证明故障消失 → 按影响范围扩大回归测试 → 保存证据;测试 diff、skip 基线和只读审查 Agent 防“把测试改绿”
- **git 操作规则**:用户要求才提交;内部检查点走隐藏引用(grok conv/*);push 永远人工点头
- **任务质量评估**:固定任务与起始环境,先检查最终产物和执行过程,再用视觉检查或 AI 评审补充主观判断;完整版本信息、未参与调优的测试集、单变量对照和线上小流量试运行共同保证结果可信
- **模型选择**:按任务类型和难度分别运行 eval,比较质量、稳定性和每个成功任务的成本;有数据再自动选择,换模型会断开缓存
- 提速要同时决定何时执行工具、每个工具能否并发,并确保一个调用失败不会拖垮其他调用
- **稳定前缀可以换来更高缓存命中率**:按七类常见原因排查,再落实八条做法;从日志恢复出的前缀逐字稳定只能保留命中机会,不保证 provider 一定命中
- **会话可信记录、运行指标和安全审计要分别保存**,再用 session/turn/attempt/tool/job/goal IDs 关联起来
- 可靠性工程与模型强弱无关——模型再强,网络照样会断

到这里,Agent 已经能够处理上下文、工具、沙箱、权限,以及约束、验证和纠正。下一章把 Agent 的事件流接到前端:流式渲染、根据事件重建状态、审批、重连与对话恢复;后续章节再汇总架构决策与组织实践。
