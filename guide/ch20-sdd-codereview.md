# 第 20 章 基于 Claude Code 的 AI 实践

::: info 本章要解决的问题
第二部分讲了怎样实现一个 Agent；对多数团队，更现实的问题是：不自研，怎样把 Claude Code 这类现成 Agent 长期用好。

- skill、MCP 和 hook 各自适合承担什么；
- SDD（spec-kit、super-powers）解决什么问题，团队怎样把它变成自己的工作流，路由与编排为什么是核心；
- 为什么团队熟悉 AI 之后 SDD 会变“重”，工作流重心怎样迁移到 CodeReview；
- 工作流在组织交付中处于什么位置。
:::

## 20.1 现成 Agent 之上，团队能加什么

第 17 章介绍过 Agent 的扩展机制。围绕 Claude Code，团队的投入主要落在四个扩展点上：

| 扩展点 | 承载什么 | 典型用法 |
|--------|---------|---------|
| skill（SKILL.md） | 流程、规范、领域知识 | 需求检查、模块知识查询、发布前检查；模型按需读取 |
| MCP | 内部系统的工具通道 | 日志、需求平台、设计稿、知识库查询 |
| hook | 生命周期事件的确定性逻辑 | 会话开始注入规则与知识库清单；工具调用前后记录哪些编辑来自 AI；结束时与提交级统计核对 |
| 工作流 | 统一的安装与初始化 | 一条安装命令、一条初始化命令，让每个项目使用同一组 skills、hooks 和知识库格式 |

统一工作流解决的是两个最常见的落地问题：“只有少数人会用”（能力没有分发）和“每个项目做法不同”（经验无法复用）。工具集本身不是 Agent——模型、循环、权限都由 Claude Code 提供，团队做的是把项目知识和流程挂在它上面。

hook 的设计有一条重要纪律：**每种 hook 只记录自己能够准确观察到的信息**。例如工具调用前后能观察到文件 diff，就记录编辑归属；不要让 hook 去推断“这段代码为什么这样写”——那不是它看得见的东西。

## 20.2 Spec 驱动（SDD）：从 spec-kit、super-powers 到各自的工作流

多数人拿到 Claude Code 这类 Agent 的第一反应，不是“它不会做”，而是“不知道怎么合理使用”：提示从何写起、任务怎么拆、上下文给什么、什么时候该让它停。SDD（Spec Driven Development）回答的正是这个问题——它不改模型，而是**把“用 AI 之前先想清楚”做成一套流程**。

### 两个常被当作起点的实现

| 实现 | 形态 | 流程 |
|------|------|------|
| **spec-kit**（GitHub） | 命令流 | specify → clarify → plan → tasks → implement |
| **super-powers** | 技能体系 | brainstorm → plan → implement → review |

大部分技术团队并不直接照搬，而是借鉴它们的骨架，实现各自的工作流。

### 机制：大量前置询问

动手之前，Agent 反过来追问——要解决什么、边界在哪、约束是什么、怎么验收——把一段模糊的想法逼成一份结构化的 spec，再由 spec 生成计划、按计划实现。

::: tip 核心思想
**想得清楚，就能做得清楚。** AI 生成的速度早已不是瓶颈，输入信息的质量才是；前置询问就是把质量从“碰运气”变成“流程保证”。
:::

### 团队定制：加维度、接流程

研发团队在这副骨架上做两件事：

- **加维度**：把通用追问换成研发视角的检查——技术方案、接口协议、上下游影响、测试策略，以及 PRD、设计稿、埋点文档这类业务输入；
- **接流程**：把工作流挂进自己的研发过程（需求评审 → 开发 → CR → 发布）。

一个实际样本：**需求门禁**固定检查八类信息（从 PRD 到代码上下文），每项先判断是否适用、再判断是否完整，信息不足即 BLOCKED——这是第 13 章 fail-closed 原则在流程上的应用：**能强制检查的规则，不要只写成提示**。

### 核心是路由与编排

场景多起来之后，工作流的核心就浮出来了。研发场景远不止一种——新页面、组件重构、bug 修复、脚手架、联调、发布检查——各自需要的步骤、skill 和提示词都不同；让一条固定流程硬套所有任务，要么过重、要么漏检。工作流真正要做的是两件事：

- **路由**：判断当前任务属于哪类场景，选中对应的工作流分支；
- **编排**：把该分支的 skill 子集、提示词和检查按需组合注入——不同场景看到不同的“流程上下文”，而不是全量塞进每一次会话。

这正是第 17 章的发现在研发流程上的投影：**流程也是上下文，同样按需加载**。

路由本身有一个真实教训：早期版本曾用 PreToolUse hook 强制所有任务先经过一个“路由” skill，后来主动移除——强制入口防住了绕过，却打断使用、抬高维护成本。落点依旧是：**可验证的检查（信息齐不齐、命令能不能跑）才值得强制；路由与流程偏好，交给目录、描述和按需调用**。

## 20.3 SDD 的问题：重心从 Spec 迁移到 CodeReview

SDD 成立有一个隐含前提：**写 spec 的成本 < 返工的成本**。这个前提正在变化：

1. 团队对 AI 越来越熟悉，描述需求的表达成本下降；
2. 更关键的是，AI 让“改”的成本骤降——生成、修改、重写一段代码的单位成本都下降了。

当改动便宜到一定程度，“先写完整 spec 再实现”的重流程性价比开始倒挂：大家更倾向**边做边想**——快速让 AI 产出可运行的结果，通过评审和迭代收敛，而不是在动手前把所有细节想清楚。工作流的重心因此从**事前的 Spec** 迁移到**事中的 CodeReview**：AI 产出快，评审成为主要的质量闸门。

评审成为主闸门之后，新的问题随之而来：**评审本身的质量怎么保证**。普通 AI 对“改动内容本身”的审阅是称职的——圈复杂度、边界与溢出风险、规范与风格，这些都能从 diff 里直接看出来。但它看不见 diff 之外的三件事：

- **隐含的链路**：这个函数的改动会传导到哪些下游调用，不沿着调用链走一遍就不知道；
- **影响面**：哪些业务路径依赖这段代码，静态的 diff 回答不了；
- **业务场景匹配**：改动是否真的符合这次需求的业务语义——这需要业务知识，而业务知识不在 diff 里。

这三件事单靠通用 AI 很难审得完善，正是 CodeReview 驱动之后要重点投入的地方：让评审从“看得出代码好坏”升级为“说得清业务影响”。第 21 章会介绍一种思路——把业务知识沉淀成可检索的结构，让评审时有据可查。

::: warning 不要从一个极端到另一个极端
Spec 没有消失，而是变薄、变晚。大改动、跨端协作、高风险任务，前置对齐仍然划算；小步、探索性任务，评审驱动更合适。判断标准是“前置成本与返工成本的比例”，不是信仰。SDD 变重说明的是它的适用范围在收窄，不是它错了。
:::

## 20.4 给工作流一个诚实的定位

到这里需要降温：工作流——无论 Spec 驱动还是 CodeReview 驱动——**只是某个研发团队在“写代码”这一小段里的实践**。它有用：门禁拦下过信息不全的任务，评审挡住过带病的改动。但**有用到什么地步，难以证明**——任务级的对照缺少干净基线，收益又混在模型版本、人员与需求类型的波动里；多数证据停留在“用的人觉得顺”，而不是“指标显示更好”。怎样逼近可证明，是第 22 章的主题。

把镜头拉远到**组织交付**，它的占比更小：一个需求从澄清、设计、编码、联调、测试走到发布与运维，编码只是一段，而工作流优化的又是编码里“AI 怎么用”的那一小段。组织级提效更大的杠杆在别处——知识怎样沉淀、怎样找得回（第 21 章），指标怎样定义（第 22 章），交付物形态怎样变（第 23 章），以及 AI 在全流程中的位置（第 24 章）。

所以合理的期待是：工作流抬高的是**单团队用好 AI 的下限**——便宜、可复制、可撤回，值得做；但它撑不起组织提效的上限，不必神化。它是第 24 章全景图里的一格，不是图本身。

## 本章小结

| 做法 | 一句话 | 取舍 |
|------|--------|------|
| skill/MCP/hook/工作流 | 把项目知识和流程挂在现成 Agent 上 | 团队维护的是知识与检查，不是 Agent 本身 |
| SDD 工作流 | 借鉴 spec-kit/super-powers 的骨架，用前置追问把想法逼成 spec | 想得清楚，才能做得清楚；再叠加技术维度与自家流程 |
| 路由与编排 | 按场景动态选择工作流分支、skill 子集与提示词 | 流程也是上下文，按需加载；可验证的检查才强制 |
| SDD → CodeReview | 改动成本下降使重心从“事前想清楚”移到“事中把关” | spec 变薄变晚，按任务风险选择形态 |
| 评审的质量把控 | AI 审得了 diff 本身（复杂度/溢出风险），审不了隐含链路、影响面、业务场景匹配 | CodeReview 驱动后的投入重点；第 21 章给出一种思路 |
| 工作流的定位 | 单团队编码场景的实践；收益难以证明，组织交付中占比更小 | 抬高下限，撑不起上限，不必神化 |
