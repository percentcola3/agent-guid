# 第 21 章 基于代码的业务知识图谱：在 RAG 与自检索之间

::: info 本章要解决的问题
Agent 要改对代码，先要找对代码。但业务语言和代码符号之间天然存在鸿沟——“下单入口的算价逻辑”并不会出现在任何函数名里。

- 为什么"标配 RAG"在模块级业务知识这个场景太重；
- 为什么全靠 Agent 自检索又不稳定；
- 一个中间层方案——基于代码构建的业务知识库——怎样工作，换来什么，付出什么；
- 缺陷 case 库怎样与业务知识互补，让评审与业务分析有实证可依；
- 知识库怎样自动更新与补充，形成知识积累的循环。
:::

## 21.1 三条路线各自的困境

**向量 RAG 太重。** 切片、嵌入、向量库、更新管道，每一环都要维护；代码高频变更导致索引持续漂移；多跳问题（“这个字段从哪来、到哪去”）需要组合多个片段，单次相似度检索经常给不出完整答案；结果也难审查——给不出 `file:line` 级证据，无法核对。这不是说 RAG 不能用，而是在“模块级业务知识”这个场景，管道成本与命中收益不成比例。

**Agent 自检索不稳定。** 第 10 章讲过 grep/read 逐步查找的路线：轻量、永远基于最新代码。但它依赖模型当轮的检索状态——关键词选得好不好、要不要再跳一次，每次都不完全一样；检索本身消耗的 token 和时间也不少。最关键的是语义鸿沟：业务词和代码词对不上，靠模型猜关键词，成功率天然有波动。

**沉淀文档会过期。** PRD 从评审到上线之间，就已经产生很多 gap——开发中的决策变更、口头确认的边界、临时砍掉或新增的需求，都不会回到文档里；纯 PRD 式的沉淀，往往无法代表最新的业务知识。再加上它和代码没有绑定关系：代码改了文档不改，越积越不可信，最后没人再看。

三条路线的共同缺口：**缺一个介于“原始代码”和“模型上下文”之间的、稳定且可审查的业务知识层**。

## 21.2 中间层：按模块构建的知识库

做法是为每个业务模块维护一个 `docs/<module>/` 知识库，内容按读者和用途分三层：

```text
product/     给产品和模型：业务说明 / 页面字段逻辑 / 常见改动会影响什么
frontend/    给开发和模型：模块结构与调用关系 / 改动影响 / 已知问题和状态
cases/       给评审和模型：缺陷 case 库——现象、根因、影响面、修复方式、关联业务场景
navigation/  给检索程序：JSON 关系数据——文件图（import/call/type/event/
             store/component-ref 六种关系）、聚类与重要度、状态机、路由
manifest.yml 业务术语清单、上次扫描的基线提交、必须覆盖的内容
```

其中 `cases/` 是与业务知识互补的另一半。业务知识回答"系统是怎样设计的"，case 库回答"它在哪里坏过"。对 CodeReview（第 20 章）它尤其值钱：评审最难的三件事——隐含链路、影响面、业务场景匹配——有了历史 case 就有了**实证锚点**，"上次改这个字段，购物车算价错了"比任何推理都有说服力。注意 `cases/` 不由代码扫描生成，它由 21.4 的补充循环维护。

生成业务知识的方式是**确定性工具与 LLM 的分工**：AST 负责静态关系，LLM 负责静态分析够不到的部分。展开成一条五步流水线：

**第一步：解析——选哪一级工具。** 代码解析有三档精度：字符串匹配（等于 grep，不算解析）；Tree-sitter 一类通用解析器（快、语言覆盖广、容错好，但只有语法树，没有类型信息）；编译器级解析（swc、Vue compiler、tsc——精确，带类型和模板语义，代价是绑定特定语言与工具链）。自建方案选编译器级：前端仓库的语言收敛在少数几种，精度优先。

**第二步：关系抽取——从 AST 到图。** 六种关系的抽取难度完全不同：

| 关系 | 抽取方式 | 难点 |
|------|---------|------|
| import | 语法层直接可得 | 几乎没有 |
| call | 函数名匹配 + 类型推断 | 动态分发（回调、高阶组件）需要类型信息才能定位真实目标 |
| type | 类型系统查询 | 依赖编译器；跨文件类型要等解析完整个项目 |
| event | 事件名注册/触发的配对 | **事件名是字符串**，纯 AST 找不到”谁监听了谁”——LLM 补充的主战场 |
| store | 状态读写的隐式依赖 | selector、computed 把依赖藏进函数体 |
| component-ref | 模板里的组件标签 ↔ import 映射 | 框架各有一套约定（Vue 模板、JSX），要按框架写适配 |

**第三步：聚合——从文件到模块。** 有了关系图，Louvain 聚类把耦合紧的文件分成组（对应”模块”），PageRank 计算每个文件的重要度（被引用多的优先呈现）。思路和打包器做依赖分析、code-splitting 是同一套。

**第四步：补全与标注。** 动态 import、事件总线、运行时行为，静态分析够不到，由 LLM 阅读源码后补充——铁律不变：**没有源码证据的结论必须标注”未验证”**，会话开始时也提醒模型不要把推测写成事实。

**第五步：增量——不每次全量重建。** 按文件变化程度分级处理——内容 hash 未变则跳过；仅注释变化只更新时间戳；字段变化只重新分析字段的来源与去向；只有结构性变化才重写模块文档并全量重扫。

### 与现成方案的对比

自建不是唯一路线。社区已有两类现成方案，先看清楚它们解决到哪一层：

| | 自建模块知识库（本节） | CodeGraph 一类社区工具 | LSP 工具（grok、dsh 内置） |
|--|--|--|--|
| 是什么 | 编译器级解析 + 六种关系 + 分层业务文档 | Tree-sitter 抽取符号与边，存本地 SQLite，文件监听自动增量同步，通过 MCP 提供”一次调用返回调用链 + 影响面”的查询 | 直连语言服务器，暴露四类点查询：定义、引用、实现、悬停信息 |
| 关系精度 | 高（编译器级 + 证据标注） | 中（语法级抽取，框架常见模式做了专门识别） | 最高（编译器本体，类型级） |
| 新鲜度 | 扫描时点，靠增量分级弥补 | 文件监听自动同步（秒级） | 永远最新——查询时读的就是当前文件 |
| 业务语义 | **有**：product 层、业务术语清单——核心差异 | 无，只有代码结构 | 无，只到语法与类型层 |
| 部署成本 | 高：自研、要长期养 | 低：装上即用，完全本地 | 中：每种语言一个 server，要管进程 |
| 分析能力 | 聚类、重要度、影响面、跨文档综合 | 调用链、影响半径、全文检索 | 单点跳转；多跳靠多轮往返 |

（社区工具迭代快，具体能力以其当前版本为准。）

**怎么选**：个人或小团队，CodeGraph 或 LSP 工具开箱即用，先解决”找到代码”；当你要回答的是**业务问题**——“改这里会影响哪个业务流程””这个字段从哪来到哪去”——现成方案就不够了，因为业务语义不在代码图里，而在人对代码的解读里，这一层没有现成货，只能自建。三条路线也不互斥：dsh 和 grok 内置 LSP 工具解决精确跳转，知识库解决业务理解，各自干各自的活。

## 21.3 怎样把知识库交给 Agent

关键是**先给清单，不给正文**（第 9 章的上下文预算原则）：会话开始时扫描所有模块的 manifest，把可用知识库的清单注入新会话（数量有上限），Agent 因此先知道“有哪些资料可查”，需要细节时再按需读取，不把知识库整体塞进上下文。

查找资料有两种方式，各有代价：

- **人工可读的路由表**：一张“问题类型 → 文档 + 具体行号”的表。简单、容易审查，但只能找到生成时列出的问题类型；
- **带索引的探索查询**：为文档元数据（别名、常见问题、实体）和“结论对应哪些代码证据”建索引，按命中字段、词数、标题和正文评分，再沿代码关系向外扩展 2~3 层。覆盖面广，但索引本身是又一层要维护的东西。

## 21.4 知识库的更新与自动补充：让知识积累起来

知识库不是建好就完事的静态资产，它有两条更新循环。

**第一条：代码驱动的增量更新**（21.2 第五步）：代码变了，按变化程度分级刷新对应文档与关系数据——hash 未变跳过、结构性变化才重扫。这条循环保证业务知识"不与代码脱节"。

**第二条：事件驱动的知识补充**——case 库的主要来源。代码扫描永远扫不出"这里曾经踩过什么坑"：缺陷发生在开发与使用过程中，也只能从开发与使用过程中回收。做法是一条流水线：

```text
会话与任务记录（第 22 章的 case 事件）
  → 筛选：只留严重 bug 和有复用价值的问题——不是所有问题都值得入库
  → 抽取：现象、根因、涉及模块与文件、影响面、修复方式、关联业务场景
  → 闸门：AI 负责抽取，人工确认后才入库
  → 反哺：评审时命中 case 库即预警"这类改动上次出过什么问题"；
          业务分析时，"影响什么业务"有实证案例而不只是推理
```

三条纪律：

1. **抽取可以自动，入库必须人确认**——与第 17 章经验沉淀同一条规矩：一次偶然修好不等于可复用的知识，证据（任务记录、diff、用户确认）要一并保存；
2. **case 要带来源与时效**——记录发生在哪个版本、哪次任务；代码大改后旧 case 可能失效，引用时要能回答"这还成立吗"；
3. **宁缺毋滥**——低价值、一次性的问题塞进 case 库，检索时全是噪音，反而把真正的高危 case 淹没。

这条循环把知识库从"代码的反光"变成"团队经验的沉淀池"：业务知识告诉你系统是怎样设计的，case 库告诉你它在哪里坏过——两者合在一起，业务分析才算完整。

## 21.5 优势与问题

**优势：**

1. **比向量 RAG 轻**：没有嵌入管道，关系来自 AST，可重复构建；
2. **结果可审查**：每条结论带 `file:line` 证据，人和模型都能核对；
3. **人机共用**：产品读 product/，开发读 frontend/，同一份知识服务两类读者——这是纯技术方案换不来的组织价值；
4. **与代码变更绑定**：manifest 记录扫描基线，“知识是否过期”是可判断的；
5. **case 库给评审实证锚点**：业务分析从"推理会影响什么"升级为"上次实际坏过什么"——第 20 章三件难事的数据支撑。

**问题：**

1. **维护是长期工程**：扫描、更新、版本迁移都有成本，知识库本身会成为需要“养”的资产；
2. **知识可能过期**：证据标注和增量更新只能降低风险，不能消除——结论仍以代码为准；
3. **评测难**：知识库回答得对不对，必须由人确认（第 22 章），禁止 AI 自评；评测要覆盖“知识库里没有答案”的情况，检查系统能否承认不知道；
4. **中间层有自己的偏差**：生成时的视角会固化——没被问过的问题类型，路由表和索引都不覆盖。

## 本章小结

| 路线 | 一句话 | 适用 |
|------|--------|------|
| 向量 RAG | 管道重、多跳弱、难审查 | 非结构化海量文档 |
| Agent 自检索 | 轻量、永远最新、但不稳定 | 熟悉的代码库、简单定位 |
| LSP / 社区图谱工具 | 点查询最准 / 代码图开箱即用 | 找代码；无业务语义层 |
| 模块知识库（本章） | AST 定静态、LLM 补动态、证据可审查 | 模块级业务知识、人和模型共用 |

知识库加 case 库回答了"改哪里、会影响什么、以前哪里坏过"；下一章回答：这些投入到底有没有让团队变快——指标怎样设计才可信。
