# 第 22 章 AI 提效的指标是什么

::: info 本章要解决的问题
“用了 AI 到底快了没有”——这个问题比看起来难：

- 哪些常见指标不可信，为什么；
- 怎样设计可复查的事件与指标；
- 快照与 AI 分析怎样把“纠错”变成可度量的证据；
- 基于 case 的监控怎样形成“分布—迁移—趋势—动作”的闭环；
- 工作流重心从 Spec 迁移到 CodeReview 后（第 20 章），指标要怎样跟着调整。
:::

## 22.1 三个常见误区

1. **“节省了 N 人时”**。不可复查：没有发生过“不用 AI 的平行宇宙”，反事实无法审计。这类数字适合宣传，不适合决策。
2. **只看代码采纳率**。AI 生成占比高不等于结果好——它同样可能意味着审查变弱了。“人工改得更少”也许只是“没人细看”。
3. **AI 自评**。让模型判断自己的回答是否正确，会系统性高估。能由程序确认的交给程序，事实是否正确必须交给人。

## 22.2 可信指标的三条原则

- **只统计可以复查的数据**。事件不按语义去重——同一问题的历史全部保留，防止“只留好看的”；格式化改动在采集端直接排除，不算人工修改；
- **关键判断由人确认**。例如知识库问答的正确性，必须由用户确认，规则明确禁止 AI 给自己的回答打勾；
- **区分“工具已实现”与“项目已部署”**。能力版本和部署状态不同，混在一起报告会把测试数据当成线上效果。

## 22.3 事件模型：先记录，再谈指标

指标不是拍脑袋选的，而是从事件里长出来的。一套经过实践的事件模型分十类：

```text
requirement / case / dialogue / ai_activity / context_evaluation
artifact_evaluation / code_metrics / manual_evaluation
knowledge_evaluation / scan_evaluation
```

每类事件回答一个窄问题。以 case（问题记录）为例：

```json
{ "event_type": "case", "case_id": "pricing-reuse-cart-order",
  "module": "pricing",
  "question": "购物车与订单结算的算价逻辑是否复用同一套",
  "discovered_from": "knowledge",      // 问题从哪发现：需求/知识库/审查/对话/用户改动/diff
  "resolution_source": "source_code",  // 怎样解决：知识库直答/补充知识库/读源码/问用户/未解决
  "outcome": "resolved", "origin_type": "ai_independent", "case_role": "work" }
```

两个枚举字段组合起来就有了解释力：`source_code` 占比高，说明知识库经常不够用（第 21 章该补内容）；`user` 占比高，说明任务开始前缺少本应由用户提供的信息（第 20 章的门禁该收紧）。

## 22.4 快照：把“AI 第一稿”固化成证据

“纠错了多少”是最难度的指标——它要求同时知道“AI 最初交出的版本”和“最终版本”，而前者天然易失：AI 自验证一通过，就被后续修改覆盖了。快照的思路是：**在“AI 第一次自认为对了”的瞬间，把相关文件固化一份**。一套真实实践分两级：

- **计划快照**：计划文档在进入人工评审前固化 v1，此后无论被改多少轮，v1 不再变；
- **任务快照**：实现阶段每个任务有自己的验证命令；验证命令**第一次**通过时，把该任务涉及的文件快照下来，并加“v1 锁”——之后人工验证再通过也不覆盖，也禁止删掉重拍。锁的语义就是一句话：**这是 AI 独立完成、未经人工干预的第一稿**。

于是“纠错”第一次有了物证：`diff(v1, 最终版)` 就是人工与后续评审改掉的部分——可逐块复查、归因、分级。没有快照，“AI 产出被改了多少”只能靠事后回忆或 AI 自报，而两者都不可信（22.1）。

一个工程细节：快照被消费时转成结构化数据（逐块 diff 的 JSON），磁盘副本随即清理——证据要的是可复查，不是永久占着工作区。

## 22.5 AI 分析：语义判断归模型，校验与计数归脚本

拿到 v1 与最终的 diff，接下来要回答“每一处改动是什么性质”。这正是该用 AI 的地方——但边界要划死。这套实践的分工是三层：

- **AI（子代理）只做语义分类**：逐个 diff 块判断改动类型（缺少边界处理、误解需求、风格调整……）与严重级别（p0/p1/p2）；
- **脚本做一切可以确定的事**：schema 与枚举校验、证据必须是真实存在的“文件：行号”（校验脚本会真的打开文件核对）、以及全部计数与比率——AI 识别出“这里有一个值得记录的问题”，但“通过率是多少”永远由确定性代码对事件日志计算；
- **闸门放在 CLI 而不是提示词里**：lint、格式化类的改动在命令行层直接过滤——即使子代理没遵守约束，数据也不会被污染。

还有一类判断干脆不交给 AI：**事实是否正确，由人确认**。例如知识库问答的评估，规则明确“只能用目标知识库回答、不得用源码或模型常识补全”，每道题都要用户确认后才计入事件——这是整个体系里不依赖 AI 自证的锚点。AI 自评的系统性高估（22.1）不是靠更聪明的提示词解决的，是靠**不让它出现在计分管线上**。

## 22.6 基于 case 的监控：分布、迁移、趋势、动作

十类事件里最值得单独立节的是 **case（问题记录）**——它定义为“一个需求执行过程中，AI 为了正确完成必须弄清楚的**最小问题单元**”：一处业务规则、一条调用链、一个文件位置。每个 case 带六个正交维度：从哪发现（需求/知识库/评审/对话/用户改动/diff 分析）、谁主导解决、在流程中的角色、验证状态、解决来源（知识库直答/补充知识库/读源码/问用户/未解决）、结果。

两个设计决定让 case 指标站得住：

1. **不做语义去重**。同一个问题被问两次就记两条，只按事件 id 防技术重试产生的重复。理由：指标要反映**实际工作负载**——同一个坑踩三遍是比“踩过一遍”重要得多的信号，去重反而把它抹平了（这也是 22.2“同一问题的历史全部保留”的工作负载视角）。
2. **证据强制引用**。case 必须挂真实的文件行号，校验不过就落不了库——没有证据的“问题”进不了指标。

基于 case 的监控方法是一个**四步循环**（实践中按月跑）：

```text
① 看分布   模块 × 解决来源：哪些模块的 case 大量靠读源码解决 → 知识库缺口在哪
② 看迁移   source_code → 知识库直答 的比例变化：补进知识库的内容是否真的被用上
③ 看趋势   “人工修改的 case”上升 + “AI 自测失败”归零 = 验证环节出了漏洞
④ 做动作   人工修改的 case 按根因分流——知识库缺内容回流知识库，流程有洞改工作流；
           下月用同一套口径复查
```

注意 ③ 的推理：两个信号**组合**才有解释力——单独看“自测失败少”像好事，叠加“人工修改变多”才暴露“AI 自测形同虚设”。这正是下一节“指标要组合解读”的实例。

最后是诚实边界：case 指标只覆盖**走了工作流的需求**，工作流之外的开发是盲区——所以要用过程指标兜底：commit 级的 AI 行归因从 git 侧自动对账、按 diff 内容幂等，不依赖任何人主动记录。覆盖率的边界本身，也要写进报告。

## 22.7 指标分层与组合解读

| 层 | 指标 | 说明 |
|----|------|------|
| 过程 | AI 编辑占比、迭代轮数、信息完整度 | 描述工作方式的变化 |
| 结果 | 完成时间、缺陷数、返工率、回退率、评审通过率 | 描述产出的质量 |
| 佐证 | 问题发现渠道、解决渠道分布 | 解释结果指标为什么变化 |

单项指标都可以被刷。**只有组合起来、且底层数据可复查时，指标才有解释力**——这与第 18 章对 Agent 评测的要求一致：先有可信的过程记录，再有可信的结论。

## 22.8 工作流变了，指标也要变

第 20 章的重心迁移直接影响度量重点：

- **SDD 时期**看前置质量：信息完整度、门禁通过率、spec 修改次数；
- **CodeReview 驱动时期**看收敛质量：返工率（评审前后被改掉的比例）、评审发现问题的分级分布、“边做边想”的收敛速度（从开始到评审通过的过程事件数）。

一个实践细节：早期版本记录过“计划被用户改写了多少”“提交前人工修改了多少个 diff 片段”这类指标，后来从事件模型中移除了。**指标下线要明确**——旧报表里已经不存在的数据，不能继续出现在新的汇报里。

## 本章小结

- 不可复查的指标（节省人时）、单看会被刷的指标（采纳率）、AI 自评，都不可信
- 先设计可复查的事件，指标从事件里长出来；关键判断由人确认
- 快照把“AI 第一稿”固化成证据（v1 锁）：`diff(v1, 最终版)` 就是纠错的物证
- AI 分析的边界：语义分类归模型，校验、过滤与计数归确定性脚本；闸门放 CLI，不放进提示词
- case 是最小问题单元：不去重（反映真实工作负载）、证据强制引用；监控按“分布 → 迁移 → 趋势 → 动作”循环，盲区用 git 侧过程指标兜底
- 指标跟着工作流形态调整：SDD 看前置完整度，CodeReview 驱动看收敛质量
