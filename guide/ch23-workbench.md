# 第 23 章 AI Friendly 的产物：Markdown 和 HTML 交付

::: info 本章要解决的问题
AI 的产出不只是代码——还有需求文档、方案、原型和验收材料。产物的形态反过来决定 AI 的效率：

- 什么样的产物对 Agent 友好（AI friendly）；
- 以 Markdown 为核心的 PRD 交付，怎样结合知识库与 skill 做审阅、门禁与风险把控；
- 为什么采用 HTML + Markdown 双形态、以 HTML 为核心；
- 这种交付方式的优势与问题。
:::

## 23.1 什么是 AI friendly 的产物

判据有三条：**Agent 能稳定生成、稳定读取、可比较可追溯**。展开说：

- 结构明确：可解析、字段稳定，模型写入和读取都不需要猜；
- 可 diff：能进版本管理、能做评审，改动可见；
- 双通道：同一份产物，人看呈现效果，机器读结构信息。

按这三条，两种格式各占一半：

| 格式 | 擅长 | 在流程中的角色 |
|------|------|---------------|
| Markdown | 过程、决策、知识；diff 友好；可直接注入上下文（第 9 章） | 记录“为什么” |
| HTML | 布局、状态、交互；表达力远超文字描述 | 呈现“是什么” |

## 23.2 以 Markdown 为核心的 PRD 交付

PRD 是研发流程里第一份正式产物。把它做成 Markdown，是 23.1 三条判据的直接应用：结构稳定可解析、可 diff 可评审、可整段注入上下文。但价值不止于格式——**围绕它建一套审阅与门禁体系，PRD 才从"描述"变成"经过验证的输入"**。

做法是 PRD、知识库、skill 三者的组合：

```text
PRD（Markdown）
  → 审阅：对照第 21 章知识库——业务术语是否与 manifest 一致、
          涉及的改动在 product 层"会影响什么"里有没有对应说明
  → 门禁：信息完整度检查（第 20 章的八类信息，缺项即 BLOCKED）
  → 风险：命中涉及模块的缺陷 case 即预警——
          "这个字段上次改过，购物车算价出过错"
  → 人评审定稿：AI 只做对照与预警，判断由人做
```

这套体系里，**知识库提供对照的依据，skill 承载审阅的流程**——术语核对、影响面检查、case 命中各是一个可复用的技能，按第 20 章的路由与编排组合；门禁这类可验证的检查才用 hook 强制。质量把控与风险把控由此有了落点：质量靠门禁与术语一致性，风险靠影响面说明与历史 case。

PRD 定稿后向下衔接研发工作流：Agent 基于 PRD 与知识库生成**技术方案**（同样是 Markdown——涉及模块与调用关系、接口改动、影响面、测试策略），走同一套审阅，再进入第 20 章的开发与 CodeReview 循环。产物形态不变，审阅范式也不变：AI 快速产出，人负责把关——与 CodeReview 驱动是同一个范式，只是评审对象从代码扩展到了全部交付物。

## 23.3 以 HTML 为核心的交付

传统流程里，“设计”的最终形态是一段文字描述或一张静态图，实现时再人肉翻译成页面，语义损失发生在翻译这一步。以 HTML 为核心则是**原型即规格**：

- 布局、状态、交互直接写进 HTML；模型读取 HTML 还原实现，比读取文字描述的语义损失小得多；
- 一条经过验证的经验：**原型里明确写出的状态（空态、加载、错误、hover）容易被正确还原；没有写出的，要么在开发前补齐，要么在实现阶段返工**。HTML 原型的完整性，直接决定了“边做边想”的迭代次数；
- MD 与 HTML 互相引用：MD 记录决策依据与来源，HTML 呈现最终形态。改 HTML 时能追到当初为什么这么定，改决策时知道要同步改哪块呈现。

## 23.4 优势

1. **语义损失小**：“看”比“读描述”更接近实现，跨角色对齐（产品、设计、前端）有共同可视物；
2. **人机双通道**：产品看效果，Agent 读结构，同一份产物同时服务两类“读者”；
3. **产物即验收物**：HTML 原型直接作为验收对照，减少口头确认和记忆偏差；
4. **与知识库联动**：原型本身可以进入第 21 章的知识体系，成为模块知识的 UI 侧证据。

## 23.5 问题

1. **双维护成本**：MD 与 HTML 描述同一事物时，同步是持续成本，不同步会互相矛盾——约定“决策在 MD、形态在 HTML，不重复描述”可以缓解，但不能消除；
2. **保真度误导**：看起来完整不等于细节都对。原型与实现之间仍然需要第 20 章的评审和测试兜底；
3. **工具链不适配**：HTML 的 diff 与评审比 MD 费力。需要约定生成结构——稳定的节顺序、稳定的命名——生成的 HTML 才可比较；否则每次生成都是“全量重写”，评审无从下手；
4. **成本转移而非消失**：生成变便宜了，但评审和同步没有等比例变便宜——瓶颈从生产移到了校验。

## 本章小结

- AI friendly 的判据：稳定生成、稳定读取、可比较可追溯
- PRD 以 Markdown 交付：知识库做对照、skill 做审阅流程、门禁与 case 预警做质量和风险把控，定稿后衔接技术方案与研发工作流
- MD 记录为什么，HTML 呈现是什么；以 HTML 为核心 = 原型即规格
- 优势是语义损失小、人机双通道；代价是双维护、保真度误导和评审工具适配

前三章讲的是单点实践。下一章把视野拉远，看 AI 在完整研发流程中的位置。
